# Auth, TLS, WebView, codecs and distribution

Auth, TLS, WebView, codecs and distribution: read before touching lib/auth/, lib/tls.dart, third_party/ or store flavours.

## Auth (`lib/auth/`), Profile (`lib/profile/`), Rooms (`lib/rooms/`), Web App (`website/`)

`AuthService`: native Sign in with Apple (`signInWithApple`), Email OTP (`signInWithOtp`) with an optional password beside it (`signInWithPassword`), browser `signInWithOAuth(google)` + web redirect bridge (`https://synctogether.app/auth/desktop-callback` or `localhost:3000` locally) + `synctogether://auth-callback` deep link (declared in the Info.plist/manifest on macOS/iOS/Android; on Windows it is an installer concern - `.github/scripts/patch-installer-script.ps1` appends the `[Registry]` handler, so **the scheme only resolves in installed builds, never under `flutter run`**. Linux is still unregistered). The web bridge displays a "Login Successful" confirmation screen in the browser and automatically forwards the PKCE auth parameters to `synctogether://auth-callback`. Windows also needs the runner half: `windows/runner/main.cpp` calls app_links' `SendAppLinkToInstance()` first thing in `wWinMain`, because the OS delivers a URI by launching a *new* process with it as argv[1] - without the hand-off over WM_COPYDATA the callback signs a second, invisible instance in while the original waits forever. That makes Windows single-instance. `signInAnonymously` for guests, `linkIdentity` to upgrade guest→Google.

**The email password is the optional half of email sign-in, and that asymmetry is the design.** An account only has one if its owner set it in the profile (`setPassword`), and the 6-digit code always works - so a forgotten password is never a lockout, and there is deliberately **no reset-link flow at all**: signing in with a code and setting a new one *is* the reset, which is one fewer deep-link path to get wrong. Nothing tries to detect whether a password exists, because Supabase exposes no flag for it and inferring it from the identity list is wrong for anyone who signed up by code - so `setPassword` is idempotent and the control reads the same either way. It is also what makes a **demo credential for App Review possible at all**, which a code-only account can never be.

**Auth Redirect URLs in `config.toml`**: `additional_redirect_urls` is configured with `["http://localhost:3000/**", "https://*.vercel.app/**", "https://synctogether.app/**"]` so Google OAuth redirects work seamlessly across the web application, desktop callback bridge, preview deployments, and local dev server without conflicting with the native desktop/mobile URI scheme (`synctogether://auth-callback`).

**`enable_manual_linking = true` in `config.toml` is what makes `linkIdentity` exist at all, and the Supabase default is `false`.** With it off, gotrue answers `/user/identities/authorize` with **404 `manual_linking_disabled`** - not 403, not a validation error - so *every* guest→Google upgrade fails identically: the profile screen's "Sign in with Google", the room's expiry upsell, anything added later. It presents as `AuthException` inside the button's own `try`, so the friendly "Couldn't start Google sign-in - try again" fires and the advice is wrong, because no amount of retrying enables a server setting. It is an **auth config key, so it ships via `supabase config push`, not `db push`** - a local stack fixed by `supabase stop && supabase start` says nothing about production, and the two are separately deployed. Confirm which one a given stack has rather than assuming: `docker exec supabase_auth_synctogether env | grep MANUAL` locally, or probe `/auth/v1/user/identities/authorize?provider=google&skip_http_redirect=true` with any user JWT - enabled answers with an `accounts.google.com` URL.

**`AuthService.start()` (called from `_bootstrap`) must stay subscribed**, and its `onError` is the load-bearing half. supabase_flutter consumes the `auth-callback` deep link inside its *own* listener, so the code-for-session exchange runs nowhere near the sign-in button's `try`/`catch`; when it fails, `_handleDeeplink` hands the `AuthException` to gotrue's `notifyException`, which calls `addError` on `onAuthStateChange`. With no error handler attached that is an unhandled zone error - fatal in Sentry and *nothing whatsoever* on screen, which is how a TLS failure on one Windows box presented as Google sign-in silently doing nothing. Errors are promoted to a user-facing snack (via the `failures` stream, which `MainApp` renders) only inside the OAuth window `_startOAuth` opens: the same stream also carries routine background token-refresh failures, and snacking or reporting each of those is the noise that trains people to ignore both. `_startOAuth` also checks the `bool` that `signInWithOAuth`/`linkIdentity` return - `launchUrl` reports a missing browser by returning false rather than throwing, so that path was silent too.

`lib/tls.dart` (`installTlsOverrides()`, awaited first thing in `_bootstrap`, before anything opens a socket) does two things. It installs Mozilla's root program from `assets/ca/cacert.pem` - because `CERTIFICATE_VERIFY_FAILED: unable to get local issuer certificate` on Windows traces to Dart snapshotting the Windows ROOT store instead of building chains through CryptoAPI, so roots Windows would install on demand never arrive (dart-lang/sdk#52266, open). **The bundle is added to the platform's roots, never substituted for them**: `withTrustedRoots: true` is what preserves every root the machine itself trusts, including the private CA a corporate TLS-interception proxy installs - replacing them would fix the reported failure and break every managed network in exchange. That additive shape is also why a stale bundle cannot regress anything; it just stops contributing. A failed asset load reports and leaves the context null, which is precisely the old behaviour. Second, its `badCertificateCallback` **reports and still returns false** - it changes nothing about which handshakes succeed, and returning true is exactly what an interception proxy needs from us. The callback receives the certificate verification *stopped on* - the unchainable root or intermediate, not the leaf - which is what still discriminates a chain even Mozilla's roots cannot complete from an interceptor whose issuer is private by design. Supabase serves leaf → GTS WE1 → GTS Root R4 cross-signed by GlobalSign Root CA; a report naming those is a chain we should have built, anything else never reached Supabase. Reports dedupe per host+issuer per run because Realtime reconnects with backoff. `ProfileService`/`RoomService` are ChangeNotifier singletons wrapping the tables/RPCs; `RoomService.serverNow` applies the `get_server_time` offset - always use it for expiry math. `RoomService` also wraps the lifecycle RPCs (`loadMyRooms`/`extendRoom`/`resumeRoom`/`deleteRoom`/`updateMediaPosition`) and holds `myRooms` for the lobby's live-and-dormant list. `RoomScreen` (`lib/rooms/room_screen.dart`) is the room orchestrator: owns playback mode state, countdown/T-5 warning/eviction ("House lights up." popup), banners (reconnecting, file mismatch), chat panel, facecam rail, overflow menu (member list, copy invite, leave, end room), desktop + tablet + portrait + landscape + folded layouts.

## Codec support (`third_party/`, `docs/codec-support.md`, `tool/codec_probe`)

Every platform ships a **full-codec LGPL** libmpv, not media_kit's slim default (which dropped TrueHD, ProRes, DNxHD...). media_kit's `media_kit_libs_{macos,ios,android,windows}_video` hardcode the slim download with no switch, so all four are **vendored in `third_party/` and wired in with `dependency_overrides`**; only the download URL/checksum differs from upstream (a path override, so the exact-pins rule does not apply to them). `docs/codec-support.md` is the reference: per-platform versions, the contract, known differences, how to bump.

- **Windows is on a different mpv (0.41) than the other platforms (0.36)**, because no full-codec Windows build exists at 0.36. Its archive is **mirrored on our own `deps-libmpv-win-<date>` pre-release** since upstream deletes builds after about a month - that release must stay `--latest=false`, so it never becomes the repo's "latest" release.
- **macOS must not override Avcodec.** The Podfile used to overwrite media_kit's `Avcodec.xcframework` with a committed patched slim copy (PGS subtitles); that hook and `macos/Frameworks` are gone, since the full build includes PGS. Reintroducing either silently cancels the full-codec build on macOS. CI asserts `--enable-decoders` in the built app's `Avcodec`.
- **Parity is enforced, not assumed**: `tool/codec_samples.sh` makes the contract clips and `tool/codec_probe` plays them in the real player on each platform. A `known_gap_*` clip is a documented difference (FFV1 in Matroska fails on mpv 0.36), reported but not failing. Bumping any build means re-running the probe and the subtitle tests.
- The build-output cache keys in the workflows include `third_party/**`, or a changed archive would reuse the old build.

## Distribution & updates

There is **no direct distribution and no in-app updater**: every build ships through a store (Mac App Store, iOS App Store, Microsoft Store), and the store delivers updates. There is no installer, DMG, appcast or Sparkle/WinSparkle to maintain. `STORE_BUILD` still selects the store flavour (loopback webview server, StoreKit on macOS, Play consumption-only on Android). The `v<ver>` git tag is created by the `tag` job in `publish_stores.yaml` once a store job succeeds.

- **`package_info_plus` is pinned back at 9.0.1**: 10.x needs win32 ^6, and `livekit_client` → `device_info_plus` 12.x pins win32 ^5. Bumping it fails resolution until LiveKit moves.
