# Backend, database, tiers and store billing

Backend, database, tiers and store billing: read before touching supabase/, RPCs, RLS, entitlements, media sharing, IAP or moderation.

## Backend (`supabase/`)

Migration `…_multi_participant.sql`: `profiles` (auto-created by trigger on signup; guests get `Guest-xxxx`), `rooms` (code, `expires_at`, `ended_at`), `room_members` (role host/member), `messages` (chat, dies with room). All RLS-gated; room channels are **private** Realtime channels (`room:<id>`) authorized via `realtime.messages` policies. RPCs (`security definer`): `create_room` (code generation, tier-derived caps), `join_room` (expiry + `rooms.max_members`), `leave_room` (host succession → earliest joiner), `end_room` (host only), `get_server_time` (clock-skew-free countdowns), `delete_account`. `…_purge_stale_guests.sql` purges anonymous users older than 3 days daily and makes `rooms.created_by` cascade on user deletion (without it, `delete_account` and the purge fail for room creators). `supabase/functions/livekit-token` mints LiveKit tokens after checking room membership via the caller's JWT.

## Entitlements & room lifecycle (`…_premium_tiers.sql`, `lib/profile/entitlement_service.dart`)

Three tiers - guest / free / premium - decide room caps, AV, and what happens when a room runs out of time.

- **Limits are config, not constants.** `tier_limits` (tier pk; `max_live_rooms`, `max_members`, `max_session_minutes`, `max_total_session_minutes`, `av_level`, `persistent_room_cap`, `dormant_hours`, `free_extension_minutes`) seeded guest(1,4,60,60,none,0,0,0) / free(4,8,240,240,voice,0,24,0) / premium(20,16,240,1440,video,20,24,0). Tuning a tier is an `update`, not a deploy. `effective_tier(uid)` is `guest` for an anonymous profile, `premium` for an unexpired `subscriptions` row, else `free`; `my_entitlement()` returns the caller's row and is what `EntitlementService` reads.
- **The room owns its properties, not the joiner.** `create_room` denormalizes `max_members` / `av_level` / `persistent` / `dormant_hours` onto the `rooms` row from the **host's** tier. A free user joining a premium room gets 16-member, video-capable behaviour - per-seat rationing was considered and rejected as unequal in-room UX. `resume_room` re-stamps them from the resuming host's *current* tier, which is how a lapsed premium room quietly becomes a free-shaped one.
- **Room lifecycle**: `room_state(rooms)` is `live`, `idle` or `expired`. A session is `live` until its timer runs out or the host ends it. Non-persistent rooms then go `expired` (and are swept). **Persistent rooms (premium) rest as `idle`**: the per-minute `sweep_rooms` still retires the session through `retire_room` (chat wiped, media locks and R2 columns cleared), but the room is kept. An idle room is listed in the lobby, is **not joinable** (`join_room` raises `room_idle`), does not count against `max_live_rooms` (only `persistent_room_cap`), and its host starts a new session with `resume_room` (lobby "Start a session" dialog). Before this, persistent rooms read `live` forever after retirement - the lobby showed them live, then the room screen bounced everyone with the ended dialog. `resume_room` is a no-op on a `live` room (it used to reset the timer, an unlimited extension), enforces the live-room and persistent caps, and refuses admin-banned rooms. `end_room` goes through `retire_room`, so ending a persistent room returns it to idle. **Idle rooms expire**: `sweep_rooms` deletes a saved room idle longer than `app_settings.idle_rooms.ttl_days` (90; `ended_at` is the idle clock, `resume_room` resets it) so forgotten rooms stop holding a `persistent_room_cap` slot. **Non-persistent ended rooms are resumable for `dormant_hours` (24)**: the lobby's ended-room dialog offers "Resume this room" to a host while `resumable_until` is in the future, reusing the "Start a session" dialog.
- **Client tier checks are affordance only.** Every cap is re-enforced in a `security definer` RPC, so a stale `EntitlementService` costs a worse error message, never a bypass. It falls back to the free-tier shape, which understates rather than overstates.
- **`extend_room` branches on config, never on the tier name.** `max_total_session_minutes > max_session_minutes` is "this tier picks its own length" (premium → duration sheet); otherwise `free_extension_minutes > 0` is the one-off teaser, spent via `profiles.free_extension_used`; otherwise `extend_not_allowed`. Reading the tier string here is how the free tier accidentally lost its freebie the first time.
- **Free rooms get one video trial, and it belongs to the room** (`…_video_trial.sql`, `lib/av/video_trial.dart`, board 32). `tier_limits.video_trial_minutes` / `video_trials_per_day` (free 10 / 2, everyone else 0) - config, read without ever naming the tier. The first camera press in a `voice` room calls `start_video_trial`, which stamps `rooms.video_trial_ends_at` (never cleared, so end-and-resume is not a second trial) and counts against the **creator's** rolling-24-hour allowance in `video_trial_grants` (no room FK, so deleting a room does not refund it). Refusals are a `status`, not an exception. The token function grants the camera only while the trial runs **and** the endpoint allows trials (`cameraGrant` in `_shared/av_endpoints.ts`; `trial` defaults off for `*.livekit.cloud`, which bills per minute), caps the token's life at the trial's end, and returns `camera` so `LiveKitService` knows - which is why a room that fails over to Cloud mid-trial silently drops to voice and the rail hides the countdown rather than promising a camera the key cannot give. At the end the client turns its own camera off (`endVideoTrial` turns the camera off *before* withdrawing the grant, since `_syncTracks` ignores a camera it may not publish); `close_video_trials` queues `revoke_camera` on `pending_av_cleanups` as the backstop, which narrows permissions **and** server-mutes the track, because LiveKit only guarantees unpublishing when `CanPublish` itself is revoked. The ended note offers "Keep faces on" to the host only. There is deliberately **no `limit_hit` when a trial merely runs out** - a timer is not a human, and every client in the room would report it; `limit_hit {which: 'video_trial'}` fires on a `daily_cap` refusal, and `upgrade_cta_shown {surface: 'video_trial'}` fires once on the host's client when the note appears.
- **The T-5 banner is where extending lives**, and it therefore **must not auto-dismiss for the host** - it is the only affordance, so retiring it after 10 s retires the feature. Members keep the auto-dismiss; they have nothing to act on.
- **An upsell offers the cheapest move the user can actually make, and for a guest that is not a waitlist.** `PremiumTeaseDialog` has two shapes, picked by whether `onSignIn` is non-null. Null is the *upgrade*: "Get a Patron seat" on **every** platform, routed to `/lobby/subscribe`, which sells through StoreKit on Apple builds; every other build is consumption-only (`canSellPremium` is true only for Apple and Microsoft Store builds), so there the upsell stands down rather than linking anywhere. "Keep me posted" survives only for a caller that wires `onNotify` without `onUpgrade`. Locked controls teach rather than label: their tooltips (`kCamLockedTooltip`, `kReactionsLockedTooltip`) say what Premium changes and for whom. A guest is one Google sign-in from everything the dialog is describing, so theirs is a full-width `GoogleButton` on `AuthService.linkGoogleIdentity` - the same in-place upgrade the profile screen runs, keeping the user id and the session - with "Maybe later" beneath it. Offering a guest a premium waitlist was the original bug: it asked them to wait for a paid thing while a free one sat one tap away. The guest's perk list is free-tier-shaped for the same reason; listing 24-hour rooms and video facecams under "Sign in for more time" promises what signing in does not deliver. **`upgrade_cta_clicked` therefore carries `action: 'sign_in' | 'notify'`** - same event, same surfaces, so the funnel does not split, but the two intents stay separable. The lobby's room-limit dialog is waitlist-only because guests can't reach it (they raise `guest_room_limit` and get their own dialog); if that ever changes it needs the sign-in shape too.
- **Resume is client-driven, because paths are.** `rooms.media_position_ms` is written by `update_media_position` - **authority only**, on a 60 s timer plus play/pause/seek/mode-switch/leave, never the 10 s heartbeat. Local file *paths* are device-scoped and never leave the device: `lib/rooms/local_media_store.dart` keeps a `shared_preferences` map of room id → {basename, path, touched_at}, pruned against a fresh `list_my_rooms` plus a 35-day TTL. A trigger nulls the position whenever `media_updated_at` moves, so a resumed room can never seek the new video to the old video's position. The decisions are free functions in `sync_logic.dart` (`shouldAutoReopenLocalFile`, `resumeSeekPosition`) with Dart tests; the seek stands down the moment `SyncService.hasReceivedInitialState` is true, because the authority's answer beats our last durable write.
- **Positions are clamped where they enter, not where they are written.** media_kit reports a small negative position (`-41 ms`) right after `open()`, which `update_media_position` rejected with `invalid_position` on every room entry. `playablePosition` (`sync_logic.dart`, next to `resumeSeekPosition`) is applied at all three points where a player's position becomes `_position` - so the scrubber and `_skip` arithmetic are covered too, not just the write. The RPC deliberately still *raises* on a negative rather than coercing: a negative is nonsense, not a value with an obvious intent, and the guard plus its pgTAP coverage is what caught this one.
- **RLS on `rooms` is membership *or* ownership, and the `or` is why the lobby can see the room blocking a create.** The original policy was `using (is_room_member(id))`, so a creator who left could not `select` their own room at all. `list_my_rooms` is `security definer` and never noticed; `fetchLiveHostedRoom` is a plain PostgREST table read and got **zero rows**, which made `live` null and left both buttons of the guest-limit dialog silently doing nothing - no error, no log, because the null guards swallowed it. Any new direct read of `rooms` by an owner depends on this policy, not on the RPCs.
- **`end_room` accepts the room's creator as well as its acting host, but `delete_room` still does not.** A creator who left their own room was not a host-role member, so the "End that room" button in the guest-limit dialog raised `not_host` - the one action that frees their cap. The widening grants no new power: the creator can already `delete_room`, which is strictly more destructive (the row goes, versus retired-and-possibly-resumable). An acting host who merely inherited the room is unaffected and still never gets delete.
- **"End that room" ends *and then creates* - the create the user was refused is retried once.** The dialog exists only because `create_room` was blocked, so ending the blocker and stopping would leave them to press Create again for no reason; the copy already says "end it first", which implies the create follows. `_showGuestLimitDialog` therefore returns whether the room was actually ended, and `_create` retries with `isRetry: true` so a second refusal can never loop. The dialog's future is **not** the signal: `onEnd` pops before `endRoom` resolves, so the pending `Future<bool>` is captured and awaited after the dialog closes - reading the pop as success would retry into the same cap.
- **Both buttons in that dialog assume ownership, not membership.** `fetchLiveHostedRoom` finds the blocking room by `created_by`, so "Rejoin it" must go through `join_room` by code rather than `context.go(roomPath(...))` - Realtime authorizes the private channel on membership, so navigating straight in lands on a room whose channel cannot subscribe. `join_room` is idempotent for an existing member, so the same call serves both cases and repairs a hostless room on the way through.
- **A hostless room adopts its next arrival as host, and that rule is deliberately not creator-only.** `join_room` inserted `'member'` unconditionally, so anyone who left their own room and walked back in returned demoted - no `set_room_media`, no `end_room`, no kick, no transport lock. It is tier-blind, so guest, free and premium were all affected identically. The predicate is "does this room currently have a host", not "is this the creator": `leave_room` already promotes the earliest joiner, so a room only goes hostless when it empties, and `kick_member` raises `cannot_kick_host` rather than creating one. **Restoring host to the creator instead would let them take the room back off an heir who inherited it**, which contradicts the succession model - the creator's retained power is `delete_room`, not the host role. The already-a-member branch heals the same way, so an existing member of a hostless room is promoted rather than left stranded.
- **`list_my_rooms` lists what you own *or* belong to, and that disjunction is load-bearing.** The cap in `create_room` counts by `created_by`, so a membership-only listing let the two disagree: leaving a room you created drops the `room_members` row, the room vanishes from "Your rooms", and it still blocks you creating another. For a guest (`max_live_rooms` 1) that is a dead end - they cannot re-enter it, cannot reach the creator-only `delete_room`, and do not know the 6-char code, so they are locked out until it expires. The row therefore carries **`is_member`** alongside `is_owner`: a non-member cannot open the room directly, because Realtime authorizes the private channel on membership, so the lobby re-joins by code first. Ordering is `live` first then `created_at desc` - newest room on top, since `expires_at desc` sorted a fresh 5-minute room *below* a long-running one.
- **Adding a column to `list_my_rooms` means dropping it first.** Postgres refuses `create or replace` on a changed return type, and a `drop` takes the grants with it - so the migration must re-`grant execute ... to authenticated` or the RPC goes invisible to every client. That is the trap `07_grants_test.sql` exists to catch.
- **Deleting a room is the creator's power alone, and host succession does not hand it over.** `delete_room` checks `rooms.created_by`, not the `host` role - an acting host who inherited the room can `end_room` (end the session) but never delete it out from under the person who made it. `list_my_rooms` returns a server-computed `is_owner` so the lobby renders the affordance from the same fact the RPC enforces, rather than inferring it from the role.
- **The deletion broadcast comes from Postgres, not the client.** Realtime authorizes a private channel at *subscribe* time, so removing rows never ejects anyone - the same reason `kick_member` needs its `member_kicked` broadcast. `announce_room_ended` calls `realtime.send` on `room:<id>` **before** the delete, so members still watching are evicted rather than left on a room whose row is gone. It has to be server-side: whoever deletes the room is standing in the lobby, not subscribed to its channel. `end_room` goes through it too, which is what finally closes the same hole on the lobby's "End that room" button. Failure only `raise warning`s - the user asked for the room to go, and it goes.
- **`room_ended` carries a `reason`.** `deleted` gets "this room is gone" copy; anything else (including a payload from a client that predates the field) keeps the session-over copy, which for a dormancy-capable room is "waiting in your lobby". Getting this backwards tells someone their room is recoverable when it no longer exists.
- **The lobby's reload-on-exit edge is committed before it fires, and that ordering is load-bearing.** The room route is *nested* under `/lobby`, so `_LobbyScreenState` is alive and listening the whole time someone is in a room; `_evictSelf` → `noteRoomExited()` notifies it synchronously. `RoomService.loadMyRooms` then notifies again *before its first await* to raise `loadingMyRooms`, which re-enters the very listener that called it. With the "were we in a room" flag assigned after dispatching the reload, that re-entry still saw the old value and reloaded again - an unbounded recursion that froze the app (`StackOverflowError`, ANR, ~70k in-flight `list_my_rooms` requests) on every "End room for everyone". `RoomExitEdge.observe` (`room_models.dart`) exists to make the order impossible to get wrong: it commits the new state *before* returning true. `loadMyRooms` also only notifies when `_loadingMyRooms` actually flips, so a notifier that has nothing new to say stays quiet - the same defence one layer down.
- **Billing & Subscriptions: store-only.** Premium is sold only through the stores (Apple StoreKit and the Microsoft Store, see the two store editions below). There is **no web checkout** and none to rebuild. The website's `/pricing` and `/account` are informational and read-only, and `/premium` redirects to `/pricing`. The `subscriptions` table, `my_premium_sources()` and the manual/debug grants stay (a `subscriptions` row can still be a hand-granted seat), and `source = 'web'` rows are legacy. One USD price ($3.99 / $29.99) is kept; use Apple's per-territory price tiers for local pricing rather than a web price.
  - **Realtime Reactivity (`20260816000000_subscriptions_realtime.sql`)**: `subscriptions` table is published to `supabase_realtime`. `EntitlementService` (`lib/profile/entitlement_service.dart`) automatically listens to `public:subscriptions:$userId` Postgres changes and runs a debounced (200ms) reload - immediately unlocking video facecams, 16-member rooms, 24h limits, and golden crowns without requiring an app reload or restart.
  - **In-App Subscription Screen (`lib/profile/subscription_screen.dart`, route `/lobby/subscribe`)**: Renders plan benefits, sells through StoreKit on Apple builds, shows a plain "active" panel for a seat bought elsewhere, and plays celebratory confetti on activation. There is no web checkout and no browser hand-off.
  - **Local Development & Debug Grants**: Local debug builds can use the `debug_grant_premium(p_months)` RPC via `EntitlementService.instance.debugGrantPremium({int months})` (or raw SQL: `insert into subscriptions (user_id, tier, current_period_end) values ('<uid>', 'premium', now() + interval '30 days');`) to test premium features without external billing infrastructure.

**Premium has to be *visible*, not merely effective** - bigger rooms, video facecams and the extended reaction set are all capabilities that quietly work, so without a badge nobody knows they are premium and nobody in a room can tell who else is. The crown is `PTColors.premium`/`premiumBorder` (gold; the host pill stays `warning` yellow - a crown glyph and a "Host" pill are told apart by shape, not hue), rendered by `PremiumCrown` and the `GuestBadge`-shaped `PremiumBadge` in `lib/ui/identity.dart`.

- **`PTAvatar.premium` is an opt-in `bool`, and must stay one.** Doing it on the avatar covers the lobby pill, chat bubbles, the readiness roster, the overflow member list and facecam tiles in one place; letting the widget reach for `EntitlementService` itself would make it untestable and rebuild it on every unrelated notify. Whoever builds the avatar owns the lookup.
- **Other members' tiers come from `room_member_tiers(p_room_id)`, not from presence.** Presence was the cheap option and was rejected: it is self-reported, so any client could claim a crown. The RPC is `security definer`, membership-gated (a non-member gets **zero rows**, not an error - it is a cosmetic read), and answers the whole room in one round trip. `RoomScreen` caches the result in `_premiumMembers` and refetches only when a user id it hasn't resolved appears in membership or presence - **never per presence event**, which fires constantly. A lapse mid-session is not chased; the crown corrects on the next entry.
- **`effective_tier` is the single arbiter, which is what keeps guests crownless.** It short-circuits on anonymous accounts before it ever looks at `subscriptions`, so a guest with a stray subscription row still reads `guest`. The client decision is the one-liner `tierWearsCrown` in `entitlement_service.dart`; never re-derive it from a `subscriptions` read, which RLS makes owner-only anyway.
- **A crown is not an analytics event.** It renders; nobody caused it. Nothing here calls `Analytics.track`.

Anonymous sign-ins are captcha-gated: Cloudflare Turnstile is enabled server-side (`[auth.captcha]` in `config.toml`, secret via `supabase/.env`), and the client shows a "Quick check" WebView dialog (`lib/auth/turnstile_dialog.dart` - **`localhost` must stay in the Turnstile widget's hostname allow-list**). The challenge page is served from a throwaway `HttpServer` on the IPv4 loopback rather than loaded as inline data, because Windows silently discards `InAppWebViewInitialData.baseUrl`: the WebView2 backend routes initial data through `NavigateToString`, which takes no base URL and always produces an opaque origin, so Turnstile refused to issue a token and guest sign-in was impossible there. A real loopback origin is the one form every platform's webview agrees on - the YouTube embed (`lib/player/youtube/`) is served the same way. Binding a loopback server used to require `com.apple.security.network.server` in **both** entitlements files, because the macOS sandbox blocks `listen()` without it (loopback included) and a debug build would work while CI's DMG silently did not; **the sandbox is gone** now (see Self-update below) the loopback servers no longer need that entitlement, **but the Mac App Store build is sandboxed again and `Release-Store.entitlements` must keep `com.apple.security.network.server` for WebRTC**: without it libwebrtc cannot receive inbound UDP, ICE never completes and every LiveKit connect times out (`MediaConnectException`, FLUTTER-6Q). Apple rejected it once under 2.4.5 when it had no matching feature, so the review notes say facecams (LiveKit/WebRTC) receive incoming UDP media. The client skips the dialog when `TURNSTILE_SITE_KEY` is absent from `.env`, but the server still requires a token, so guest login fails without the key configured.

Windows needs one more thing before that dialog can render at all, and it is set up in `lib/auth/webview_runtime.dart` (`PTWebView.init()`, called from `_bootstrap`): **an explicit `userDataFolder` under `LOCALAPPDATA`**. Left null, WebView2 defaults that folder to the directory holding the executable and tries to create `synctogether.exe.WebView2` beside it - which is under Program Files for the admin install inno_bundle configures, so a standard user token cannot write it and the environment fails to create. All that reaches Dart is `PlatformException: Cannot create the InAppWebView instance!`, and since it surfaces asynchronously from the platform view it lands as an *unhandled* error, leaving the dialog to sit on an empty box until the 20 s deadline. Passing `PTWebView.environment` to every `InAppWebView` is what keeps it writable. `init()` also probes `WebViewEnvironment.getAvailableVersion()` first: null means the runtime genuinely is not installed (the installer's Evergreen bootstrapper never took), which is a different fix and gets its own `webview2-missing` code and its own on-screen copy - "try again" is wrong advice for a missing OS component. A *failed environment creation* deliberately does not block the dialog; it reports and falls back to the plugin's default, since attempting the challenge beats refusing it.

## Media sharing / pre-upload (`lib/rooms/media_sharing_service.dart`, `…_media_sharing.sql`, `…_staged_media_uploads.sql`, `supabase/functions/media-share`)

A host can upload the video itself, so members without the file can still watch. It is an **enhancement of local mode, not a fourth playback mode** - `media_kind` stays `'local'` throughout, and `rooms_media_shape_chk` only permits the R2 columns on `'local'`.

- **The bytes live in Cloudflare R2, not Supabase Storage.** Supabase Storage holds `avatars` and nothing else. Every operation goes through the one `media-share` Edge Function (`initiate`/`part-urls`/`complete`/`abort`/`download-url`, each with a `staged-` twin), configured by `CF_R2_ENDPOINT` / `CF_R2_BUCKET_NAME` / `CF_R2_ACCESS_KEY_ID` / `CF_R2_SECRET_ACCESS_KEY`.
- **Members play through a loopback range proxy (`lib/player/stream/`), with the presigned/edge URL as its origin; there is no P2P.** `StreamProxy` is a `127.0.0.1` `HttpServer` (random port, per-run secret path segment, Host checked) that mpv opens instead of the remote URL. It answers Range requests (206/416/HEAD) from a sparse on-disk entry (`MediaSharingCache.openSparse`: pre-sized `.part` plus a one-byte-per-chunk `.map`, chunk marked only once whole, LRU cap `kStreamCacheCapBytes` = 3 GiB enforced on start, wiped by `clearAll` on account deletion) and fills holes by fetching chunks over 2-8 parallel connections (adaptive, `ParallelismController`; `chunkBytes`/`maxParallel` come from optional hints on the `download-url` response, parsed and clamped in `DownloadUrlResult`, defaults 8 MiB / 4; chunk rounded to 4 MiB multiples to line up with the edge Worker's cache chunk). Prefetch is a window ahead of the newest reader, adjacent prefetch chunks ride one request (`kMaxFetchSpan` = 2; the chunk the playhead waits on is always its own request) and fetches no reader's window covers any more are aborted on a seek - request count is the cost lever at scale. **Expiry is handled inside the proxy** (proactive re-sign at 90% of `expiresIn`, and on 401/403, single-flight, skipped when another fetch already re-signed). Switch it off with `--dart-define=STREAM_PROXY=false`; if it cannot start (no socket, disk, size unknown) or gives up (three chunks in a row failed for good) the room plays the direct URL. Nothing is transcoded or rewritten: bytes in = bytes out. The mpv tuning (`stream_tuning.dart`: read-ahead, 256/128/80 MiB demuxer cache by device, cache-pause-initial/wait, `stream-lavf-o` reconnects) applies to remote streams only and `localFileStreamOptions` resets it - note `demuxer-lavf-o` is deliberately **not** touched, media_kit owns it (protocol whitelist) and overwriting it would break the loopback `http` open.
- **Optional edge delivery (`deploy/media-edge`, `docs/media-edge.md`, flag `app_settings.media_edge`).** When `media_edge.enabled` is true *and* `MEDIA_EDGE_SECRET` is set, `download-url` (the only action that returns a stream URL; the staged twins never do) returns `https://<base_url>/v1/<key>?exp=&sig=` instead of the presigned S3 URL, with the same TTL and the same response shape plus optional `chunkBytes` / `maxParallel` hints (from `media_edge.chunk_bytes` / `max_parallel`, clamped 4-32 MiB in 4 MiB steps and 1-8, defaults 8 MiB / 4; the 4 MiB step is the Worker's cache chunk, `WORKER_CHUNK_BYTES` must track `CHUNK_SIZE`). The Worker reads the bucket through an R2 *binding* and caches aligned 4 MiB chunks in `caches.default` under a key with no token in it. **Either condition missing means the presigned URL exactly as before** (self-hosters, local dev, any flag-read error); the row ships `enabled:false`. The HMAC scheme exists twice (`supabase/functions/_shared/media_edge.ts` and `deploy/media-edge/src/sign.ts`) and both tests pin the same vector - change one, change both. The Worker never transcodes or rewrites bytes, and an edge URL still expires, so `_recoverFromStream403` applies unchanged. Cached chunks outlive object deletion by up to `EDGE_CACHE_TTL_SECONDS` (6 h) in each colo, which `cleanup-r2` does not purge.
- **Presigned URLs expire, so a long film will 403 mid-playback.** `_recoverFromStream403` re-signs, reopens, seeks back, **and restores the selected audio and subtitle tracks** - that last part is the easy thing to drop, and dropping it silently resets the viewer's track choice on every re-sign. With the proxy on, a 403 never reaches mpv (the proxy re-signs); `_recoverFromStream403` remains for the direct-URL fallback and for the proxy giving up, and still restores tracks.
- **Stream health and the connection notice (`stream_health.dart`, `stream_notice.dart`, `stream_session.dart`).** `StreamHealthMonitor` samples the proxy's origin counters (or mpv `cache-speed` without a proxy) once a second and tracks stalls (only while playing, after the first frame). Silence is the default: a verdict needs (>= 2 stalls in 60 s or one > 8 s) AND measured origin throughput < 0.9x the file's bitrate (size*8/duration). Then a link probe (`link_probe.dart`: 4 parallel ranged reads of the same object for ~4 s, the proxy's own concurrent bytes counted in) decides who is short: >= 1.3x required means it is our path (silent escalation: `proxy.boost()` + deeper mpv buffer, at most two neutral 'Buffering a little more' notes per file); < 1.0x is the only case that shows the connection notice (once per file, info style, dismissible); in between is inconclusive and silent. 'Buffer ahead' holds the member at `loading` in presence (`_computeReadiness`) until ~30 s are ahead, capped at 90 s, so one slow link cannot hold a room; 'Start anyway' releases it. The only product event is `stream_notice_answered {choice}`. Design board 51.
- **Quota is two config surfaces, and they answer different questions.** `tier_limits.media_sharing` (`none`/`limited`/`full`) + `media_sharing_weekly_bytes` is the weekly allowance; `app_settings` key `media_sharing` carries `enabled` (kill switch) and the per-file caps `free_tier_max_file_bytes` / `premium_max_file_bytes`. Seeds: guest `none`, free `limited` at 2.5 GB weekly / 2 GB per file, premium `full` at 10 GB per file.
- **Premium's `media_sharing_weekly_bytes` is `0`, and `0` means unlimited, not zero.** The weekly check only runs under `media_sharing = 'limited'`. `Profile.remainingWeeklyBytes` returns the sentinel `-1` for unlimited, which every caller must special-case.
- **The client's copies of these numbers are hard-coded mirrors, not fetched.** `EntitlementService.mediaSharingMaxSizeBytes` inlines 10 GB/2 GB and `TierLimits.fallback` inlines the 2.5 GB. Changing a quota therefore means `tier_limits`, `app_settings`, `entitlement_service.dart`, `media_quota_dialog.dart`, `website/lib/constants.ts` and `docs/feature-toggles.md` - client checks are affordance only (the `tier_limits` doctrine), but a drifted mirror still refuses an upload the server would have allowed.
- **The two slot RPCs report failure in two different shapes, deliberately matched on both sides.** `request_upload_slot` *raises* (`upload_quota_exceeded`, `active_upload_in_progress`, `upload_cooldown_active`…); `request_staged_upload_slot` *returns* a jsonb envelope (`quota_exceeded`, `file_too_large`, `concurrent_upload_active`…). `MediaSharingException.fromError` matches both spellings; adding a code to one side only degrades it to the generic "Upload failed. Please try again."
- **Both slot RPCs are `service_role` only** (`20260906110000_security_and_privilege_hardening.sql` had to *revoke* first - a bare `grant … to service_role` leaves PUBLIC's default intact). `clear_media_sharing` is the one granted to `authenticated`, host-checked inline.
- **The Edge Function creates the R2 multipart *before* calling the guard RPC, and aborts it if the RPC refuses.** That order exists so the RPC can record a real `upload_id`; reversing it needs a different compensation.
- **`set_media_upload_state` must null `media_upload_id` exactly when it moves to `'ready'`**, because `rooms_media_shape_chk` requires `media_r2_key`/`media_file_size` present *and* `media_upload_id` null in that state. The `'uploading'`/`'failed'` branches are deliberately unconstrained.
- **Staged uploads are the lobby pre-upload: bytes in R2 under `users/<uid>/staged/…` while no room exists yet**, claimed by `create_room(…, p_staged_id)`. Two sharp edges: `expires_at` is **one hour** from `staged-initiate`, so a slow upload plus a slow user fails the claim with `staged_media_invalid` even though the object is fine; and the weekly debit lands at `'ready'`, **before any room exists** - an abandoned staged upload costs quota, and cancelling refunds nothing.
- **Starting a second staged upload silently destroys the first** and increments the abort counter, which matters because the staged ladder penalises *every* abort and cools down 30 minutes at 5. The in-room ladder is different again (penalty only above 50 MB, 1/5/15 minutes). Only a `'ready'` resets the counter. Unifying them changes user-visible behaviour on both paths.
- **Nothing deletes from R2 synchronously.** Writers enqueue to `pending_r2_deletions` - `set_room_media`, `request_upload_slot` (orphaned re-upload), `set_media_upload_state('failed')`, `clear_media_sharing`, `retire_room`, plus BEFORE DELETE triggers on `rooms` and `staged_media_uploads`. `clear_staged_upload` relies on its trigger and must **not** re-add an explicit insert (that was the point of `20260830100000_r2_cleanup_automation.sql`). The `cleanup-r2` function drains the queue and **drops a row for good at `attempts >= 5`**, so a permanently failing key leaks by design.
- **`invoke_r2_cleanup` ships inert.** Its `app_settings.r2_cleanup.endpoint_url` seeds NULL, so the 5-minute cron no-ops until an operator sets it; failures only `raise warning`. Confirm it is populated before assuming anything has ever been collected.
- **A date night can adopt a staged slot** (`staged_media_uploads.date_night_id`, see `docs/agent/pairing.md`). Three things differ from the lobby's use: the slot lives until the night plus a day instead of an hour; the profile's `active_upload_staged_id` lock is released at adoption (so a later lobby slot does not destroy it); and `uploadStagedFile(keepSlotOnFailure: true)` leaves the slot in place on a non-cancel failure so `resume:` can continue it. **`clear_staged_upload` skips the abort penalty for a ready date-night slot** (its expiry sweep calls it; a finished upload that outlived its night was not abandoned). A slot adopted by a night is excluded from none of `cleanup-r2`'s sweeps, which is intended: if the night's own sweep has not got there first, the expiry sweep frees it.
- **A late joiner is auto-waived while shared media is streaming.** `_handlePresenceSync` waives an arriving member until they reach `ready` when `_isAuthority && _roomPlaying && _mediaUploadState == 'ready'`, so a room does not stop dead every time someone arrives mid-download. It is the gate's waiver machinery, not a second mechanism.
- **`retire_room` clears the R2 columns**, which is why a resumed or persistent room comes back without its shared video. That is deliberate - the object is already queued for deletion.

## Apple App Store edition (`isAppleStoreBuild`) and In-App Purchase

The Mac App Store build sells Premium through **StoreKit 2**, and premium bought on another rail (a hand-granted seat, later Microsoft Store) unlocks it too. The previous shape - a single free tier with premium stripped out - was rejected by Apple repeatedly under 3.1.1: a free member in a premium host's room still *reaches* premium, and no amount of hiding changes that. 3.1.3(b) permits honouring a web purchase only when the same thing is also for sale in the app, so it now is. Windows needs none of this: Microsoft Store policy lets non-game apps use their own commerce, which is why Windows sells through the Microsoft Store (next section).

- **On iOS, `isAppleStoreBuild` is true for every build**, regardless of `STORE_BUILD` - Apple is the only way an iOS build is ever distributed, so a debug or TestFlight build must sell through StoreKit like the release. macOS still needs `STORE_BUILD=true`, because its direct build sells through the web checkout. `publish_ios_app_store.yaml` archives with automatic signing, authenticating `xcodebuild` with the App Store Connect API key (`-allowProvisioningUpdates`), and sets the build number from `github.run_number`, because pubspec carries a bare version.
- **Two rails, one arbiter.** Apple subscriptions live in `apple_subscriptions` (`…_apple_iap.sql`), keyed on `originalTransactionId`, deliberately *not* in `subscriptions`: that table is one row per user, so the two rails would overwrite each other - a web `canceled` revoking a live App Store subscription. `effective_tier` reads both.
- **Trust comes from Apple's signature, binding from `appAccountToken`.** `supabase/functions/apple-iap/apple_jws.ts` verifies every JWS against a pinned Apple Root CA - G3 (`apple_root_ca_g3.ts`) on WebCrypto via `@peculiar/x509`: chain signatures, Apple's leaf/intermediate OIDs, validity at `signedDate`, then ES256. **Not Apple's `@apple/app-store-server-library`** - its `SignedDataVerifier` calls `X509Certificate.prototype.toString`, which Deno's node compat throws `ERR_NOT_IMPLEMENTED` for, so it rejected every genuine payload while type-checking cleanly; `apple_jws_test.ts` (`deno test`) mints an Apple-shaped chain and exercises the real code path on Deno for exactly that reason. The client sets `applicationUserName` (-> `appAccountToken`) to the Supabase user id, and `/verify` refuses a transaction whose token is not the caller - a signed transaction is replayable. `apply_apple_transaction` (service_role only, pgTAP-covered in `19_apple_iap_test.sql`) binds a purchase to one account forever (`owned_elsewhere` otherwise) and applies only strictly newer `signedDate`s.
- **Both App Store environments are accepted in production.** App Review buys with sandbox accounts against the production build; rejecting Sandbox there fails review.
- **Billing retry is grace, a refund is revocation** - the web-billing `past_due` rule. `expires_at` is the later of `expiresDate` and the renewal's `gracePeriodExpiresDate`; `revocationDate` revokes.
- **Finish a transaction only when retrying cannot change the answer** (`classifyVerifyResponse`). A 400, 5xx or network error leaves it unfinished - a server that cannot verify a genuine transaction looks exactly like a bad one - and StoreKit redelivers it on the next launch; finishing it would lose a paid purchase. `AppleIapService.start()` subscribes the purchase stream in `_bootstrap`, not on the subscription screen, for the same reason.
- **The store build must never steer to the web checkout** - no link, no web price, no "subscribe on our website". Terms and Privacy links are *required* (3.1.2) beside the offer, as are the auto-renew terms and Restore purchases.
- **An App Store subscription is managed only by Apple**, on any build: `my_premium_sources()` tells the subscription screen which rail entitles the account, and an Apple-only premium gets "Manage in App Store", never the web account page, which cannot cancel it.
- Secrets for the function: `APPLE_BUNDLE_ID`, `APPLE_APP_APPLE_ID`. Product ids are constants in `apple_iap_service.dart` and are permanent once created in App Store Connect.
- **No mock demo mode ships.** 2.1(a) permits a built-in demo mode only with Apple's prior approval and 2.3.1(a) forbids undocumented features; 1.6.3 had both a "Demo Review Sign-in" link and a hardcoded email/OTP pair that skipped authentication. Mock data now needs `--dart-define=DEMO_MODE=true`, which is how the store screenshots are shot and ships in no release binary. Reviewers use Sign in with Apple or guest mode; email sign-in is passwordless, so a shared demo credential is impossible by construction.
- **The camera entitlement covers profile photo capture and video facecams**, both reachable on this build now; say so in the review notes.

## Microsoft Store edition (`isMicrosoftStoreBuild`) and In-App Purchase

A Windows build with `STORE_BUILD=true` (the MSIX) sells Premium through `Windows.Services.Store`, the Windows counterpart of the Apple flow, and `canSellPremium` is true there. It mirrors Apple's shape on purpose:

- **Three rails, one arbiter.** `microsoft_subscriptions` (`20261015120000_microsoft_iap.sql`) is keyed on the Store's collection item id, bound to one account once (`owned_elsewhere` otherwise) and applied only when strictly newer by `observed_at`, through `apply_microsoft_subscription` (service_role only, pgTAP-covered in `26_microsoft_iap_test.sql`). `effective_tier` and `my_premium_sources()` read it; `EntitlementService` reads it back like the others.
- **The native half is `windows/runner/store_purchase.cpp`** (C++/WinRT, channel `app.synctogether/store_purchase`: `products`, `purchase`, `idKey`). Store calls block, so they run on a worker thread and answers hop back to the platform thread with a window message (`kStorePurchaseMessage`, handled in `flutter_window.cpp`) because `MethodResult` is not thread safe. It only works in a packaged, Store-associated build; anywhere else the Dart side shows "couldn't reach the Store". It was first written without a Windows toolchain; sandbox purchases have since been proven on Windows (2026-11-02), but only in a packaged, Store-associated build, so re-test after changing it.
- **Trust comes from Microsoft, binding from the key.** `ms-iap/ticket` hands a signed-in non-guest an Entra token for the Store audience; the app mints a Store ID key with the Supabase user id as `publisherUserId`; `ms-iap/verify` refuses a key that does not carry the caller's id (`keyBindsTo`, deliberately claim-agnostic - **tighten it to the real claim once you have decoded a real key**) and then asks the Store **purchase** API (`recurrences/query`, `ms_subscriptions.ts`) what subscriptions that key holds. Only `MS_STORE_PRODUCT_IDS` count. **Subscriptions are not in the collections API**: it lists only Application/Durable/Game/UnmanagedConsumable, so a collections query returns the app itself and nothing else for an account that plainly holds a subscription (it was a long way to learn that). That is also why the key must come from `GetCustomerPurchaseIdAsync` with a token for the `…/b2b/keys/create/purchase` audience, not `GetCustomerCollectionsIdAsync`. Neither API sees anything until the Entra app's client id is registered under the app's Partner Center **Services > Product collections and purchases** (up to two ids; allow up to 16 hours - an unregistered app authenticates fine and just gets an empty answer).
- **There are no server notifications.** `MicrosoftIapService.start()` re-verifies on `initialSession`/`signedIn`, so a renewal is picked up at the next launch and an account that stops launching simply expires. `sync(silent: true)` makes that launch check quiet.
- **Never steer to a website**, same as the Apple build; the manage button opens the Microsoft account subscriptions page, which is Microsoft's, not ours.

## Google Play edition (`isGooglePlayBuild`, `canSellPremium`)

An Android build with `STORE_BUILD=true` is the Google Play build, and it is **consumption-only**. Play's Payments policy requires Play Billing for digital subscriptions and forbids steering - no link, button or copy that leads to another way to pay - and we do not sell through Play Billing. Premium bought on the web or the App Store still unlocks (the policy permits that); nothing offers, prices or links to it.

- **Every upsell checks `canSellPremium`, and a new one must too**: the lobby chip, room-limit and ended-room dialogs, the room's expiry tease and its Premium button on eviction, the locked camera, the video trial's "keep faces on" end note (`_offersKeepFaces`) and the reaction `+`, the media-quota dialog, the profile's plan row and handle row, the leaderboard's Patron card. Each one disappears or falls back to plain copy; `_showPremiumTease` turns into an info snack.
- **Guest sign-in prompts are not sales** and stay on Play, which is why `_showPremiumTease` only stands down when `onSignIn` is null.
- **The subscription screen links nowhere on Play**, not even "Manage subscription" for a seat bought elsewhere. Free users there see one plain line; premium users see that the seat is active.
- Selling Premium on Play later means Play Billing (a third rail beside `apple_subscriptions` and `subscriptions`), not relaxing this gate.

## Moderation (`lib/rooms/moderation_service.dart`, `…_ugc_moderation.sql`)

Guideline 1.2 wants an agreement before sign-in, a way to flag content, a way to block abusive users - where blocking "notifies the developer and removes it from the feed instantly" - and published contact information.

- **A block is account-scoped and keyed on user id.** The original was an in-memory `Set<String>` on `RoomScreen` keyed on *display name*: it died on leave, so the same person was unblocked by walking into the next room, and a rename walked straight back into the feed.
- **Blocking files its own report.** The common case is somebody who blocks and closes the app, and that signal is the one worth having - which is exactly what "notify the developer" asks for. It is wrapped so a rate-limited report can never fail the block: losing the notification is the acceptable half of that trade, losing the block is not. Only a *new* row files one, so the queue cannot be padded by toggling.
- **"Instantly" includes the reload**, so the block lives in the `messages` select policy, not only in the client. A realtime broadcast carries no RLS, so the client filters too - both halves are needed.
- **The member list is the one surface that still shows blocked people**, because it is where unblocking lives. The readiness roster also keeps everyone: the gate waits on all present members, so hiding a blocker there would make a shut gate inexplicable. Facecams and chat do hide them.
- **`content_reports` is never readable by any client** - RLS on with no policy, plus an explicit revoke, the `room_bans` pattern. Neither the reporter nor the reported can read it; triage is `service_role`. Neither it nor `recaps` carries a room FK, for the same reason: a report has to outlive the room, and the host deleting the room is not an acceptable way to destroy the evidence.
- **Copyright is a report category**, because media sharing redistributes a host's video file to the room. The takedown route and the registered designated agent live at `synctogether.app/dmca`.

**There is no YouTube account sign-in, and there must not be one.** Google forbids sign-in in embedded webviews and Apple 5.1.1(vi) treats harvesting credentials or cookies as grounds for removal; the IFrame API offers no authenticated playback to third parties, so playback is signed-out (ads included) and the URL dialog says so. `purgeLegacyYouTubeCookies()` clears what builds up to 1.6.3 banked.
