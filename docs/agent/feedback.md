# Bug reports (`lib/feedback/`)

Read before touching the bug button, the report sheet, Your reports, the discovery prompts or the `bug_reports` table. Design: canvas boards 82 (phone) and 83 (desktop and discovery).

**Why it exists.** A user who hits a bug and has nowhere to say so leaves a one-star review. The button turns that moment into a report the team can act on, and the follow-up ("fixed in 1.4.2") closes the loop. Everything below serves that: one tap, nothing to fill in, a promise that is kept.

## Invariants

- **Screenshot first, sheet second.** `FeedbackService.captureScreen` runs before the sheet opens (so it shows the problem, not the sheet) and must stay fast; `gather` fills the slower data while the user reads. Send never waits on `gather`.
- **Reached through one seam.** `FeedbackServices.instance` (defaults to `FakeFeedbackService`; `_bootstrap` installs the real one after Supabase). UI is written against `FeedbackService`, never the implementation. `BugReport.open(context)` is the only entry point; the button, shortcut, shake, More-menu row, nudges and Profile rows all call it.
- **What a report never carries:** chat text, full file paths (basename only), emails, tokens, other members' names, audio or video. The "what we send" disclosure shows the same lines the report holds, so the UI cannot drift from the payload.
- **Two destinations, independent.** Sentry feedback (screenshot and `logs.txt` attached to a captured event, so the breadcrumb trail rides along) and the `bug_reports` row via `submit_bug_report`. Either failing must not block the other; both no-op safely without `SENTRY_DSN`. The row is what powers Your reports and the fix notice, so it is the one that matters.
- **Offline is a state, not an error.** A failed send is queued on the device (metadata in `shared_preferences`, screenshot PNG as a file via `path_provider`) and flushed at launch, on resume and on a backoff timer. The user sees "Saved on this device". Classify failures with `isTransientNetworkError`.
- **Server rules.** Owner reads their own rows only; clients cannot insert, update or delete. Status and `fixed_in` change through the service role. `submit_bug_report` is rate limited (1 per 30 s per user), caps the note and context, and works for guests.
- **Copy.** Friendly and warm; never "we apologise for the inconvenience", never a raw error, and no rating ask on the success screen.

## Shake and the device model

- **Shake to report** (`shake_to_report.dart`, board 86) is phones only, on by default, with a toggle in Profile › Help and a one-time banner after the first shake-opened report. **Where a shake comes from is a `ShakeSource`** (`shake_source.dart`): on **iOS** it is Apple's own gesture (`NativeShakeSource`), so there is nothing to tune and Dart reads no sensor at all (no `sensors_plus`, no CoreMotion); on **Android** there is no system gesture, so `AccelerometerShakeSource` feeds `sensors_plus`' `userAccelerometerEventStream` to the pure `ShakeDetector` (`shake_detector.dart`). People count a shake as a full down-and-up, which is two swings, and want two of them, so the detector needs **four consecutive swings** (any direction, above 7 m/s²), each starting within 400 ms of the last; a longer pause drops the partial count and the next movement is swing one again, nothing is remembered across it (`swings` and `pauseLimit` are constructor parameters). `ShakeToReport` subscribes to the source **only while** the device is a phone, the setting is on, the app is foregrounded and the router is attached, so an idle app costs nothing, and keeps its own 2 s cooldown so a long shake never opens two sheets. A shake is the same tap as the button (`BugReport.open(source: 'shake')`) and is ignored while the app is starting (2.5 s settle, because the splash is an overlay over a live router), on `/login`, while a report is open, and while the room says fullscreen video is playing (`ShakeToReport.registerBlocker`, registered next to the room's probes). iOS decides "phone" from the device (an iPhone Duo's inner display is tablet-sized but still an iPhone); Android from a small display or a hinge sensor.
- **The iOS native hook** is in `ios/Runner/AppDelegate.swift`: `ShakeFlutterViewController` (the storyboard's view controller) overrides `motionEnded` and forwards `.motionShake` as a bare `shake` call on `app.synctogether/shake` (`ShakeChannel`; Dart installs its handler only while subscribed). `applicationSupportsShakeToEdit` is off, so iOS never shows "Shake to Undo Typing" and never keeps the shake for a text field. UIKit sends a shake to the first responder and up its chain: a focused text field sits inside this controller's view, so the shake reaches the controller through it; with no field focused nothing is first responder, so the controller claims it when it appears, when the keyboard hides and when the app becomes active, and never while the keyboard is up (it must not take focus from a field). The app delegate also overrides `motionEnded` as the end of the chain. The one case this cannot see is a hardware keyboard with a focused field, where the shake still reaches the controller through that field. **Manual checklist (the Swift cannot be unit tested):** (1) lobby, no field focused: shake opens the sheet; (2) focus the name field with the keyboard up: shake opens the sheet and the keyboard/typing is not disturbed, no "Shake to Undo" alert; (3) close the sheet, shake again after 2 s: opens again; (4) shake inside a room, then fullscreen video playing: ignored; (5) open the photo picker, dismiss it, shake: still works; (6) background and return, shake: still works; (7) turn the Profile toggle off: shake does nothing.
- **Android** is unchanged by the native hook and is the unverified side: the accelerometer path is tested with synthetic 50 Hz traces (gentle, normal and hard shakes fire; walking, a slow arm wave, a single swing and a hard put-down do not; running with the phone in a pocket does, a documented limit), but nothing has run on real Android hardware.
- **Device model** (`capture/device_model.dart`, `device_info_plus`) is the marketing name only ("iPhone 17", "Samsung SM-S921B", "MacBook Pro", the Windows product name), read once, cached, redacted, in the report summary and at `context.device.model`. It never reads an identifier (`identifierForVendor`, advertising id, serial, hardware UUID). Any failure leaves the model out and goes to `reportNonFatal`. The privacy page lists it under Bug Reports.

## Discovery (never a timer)

Five layers, quietest first: a one-time coach mark (second launch or after the first room, never over a playing film, one ripple; the rest of the window is dimmed with a hole on the lit bug button - one even-odd fill, never a blur - and a tap on the dim, Escape or "Got it" ends it as seen, while a tap on the lit button still reaches the button), a banner at a moment of need, a "fixed" banner in the lobby, Profile › Help rows, and the post-film "How's the show going?" prompt. Cooldowns: one nudge per session, 14 days after a dismissal; the review prompt at most twice a year. The prompt's "Not quite" opens the report sheet; "Great" opens the store's rating sheet; the Rate row in Profile stays visible, because the stores forbid hiding the review option from anyone.

## Instrumentation and analytics

- Diagnostics use `trace(..., category: 'feedback')` at transitions (captured, gathered, queued, flushed, sent, rate limited) with ids, sizes and durations in `data:`; `reportNonFatal` for a send that fails for a non-transient reason. Never log the note text.
- Product events go through `lib/feedback/feedback_analytics.dart` only (`FeedbackAnalytics.opened/sent/introDismissed/nudgeTapped/reviewAnswered`), and only where a person tapped: never for a coach mark or banner merely appearing. They are listed under "Reporting a problem" in `lib/analytics_catalog.dart`, which `test/analytics_catalog_test.dart` keeps honest in both directions.

## Working the board (`scripts/bugs.ts`, `.claude/skills/bug-triage`)

- **The playing film's technical details, never its name** (`capture/media_probe.dart`, `capture/media_details.dart`, board 82 pane 03). `RoomScreen` registers one `MediaProbe` per room; it shows up as the `media`, `video`, `color`, `audio`, `subs`, `decode` and `mpv` lines so we can tell whether a file's format is truly supported: extension, container, codec/profile, resolution, fps, bit depth, colour primaries/transfer/matrix/range and an HDR flag, audio codec/channels/rate, subtitle track formats, a **size band** (never the exact size), hardware or software decode and the last warnings from mpv (URLs, paths and file stems stripped, extension kept). mpv is read through `NativePlayer.getProperty` in parallel with a 400 ms timeout each and cached when the tracks or parameters change (probes are synchronous); a property that is missing just omits its line, and YouTube says only the mode and playback state. **The file name is opt-in and off by default**: it is never in a probe line, the context or the logs, and only travels when the capture has `includeFileName` set (the sheet's "Include the video's file name" switch, under "See exactly what we send", shown only while a local film is playing, off every time the sheet opens and never remembered; the revealed `file` line is exactly what travels; `BugCapture.fileName` is gathered through `FeedbackProbes.optional('media.file_name')`, `RealFeedbackService.submit` adds it as `media_file_name` and a `file` summary line only when included). The room summary line and the `media` breadcrumb no longer carry the name either.

`node scripts/bugs.ts` is the terminal side of the internal board (`list`, `show`, `find`, `looking`, `fix`, `wontfix`, `duplicate`, `reopen`, `close-from-commits`; `--local` for the local stack). It writes only through `admin_set_bug_status`, so the reason, original and version rules hold. Everything except `looking` prints a plan and needs `--confirm`. **Only the `looking` status is set while working; FIXED is set by the release skill (step 8) after every store has accepted the build**, from the commits' `Fixes-Bug: BUG-XXXX` trailers. Won't-fix reasons and duplicate links are human decisions: users read them. `fixed_in` is the first version with the fix ("fixed from X.Y.Z onward"). `close-from-commits` starts its scan at the tag of the highest version already closed on the board, not at the last tag, because the `tag` job tags a build as soon as one store accepted it.

## macOS menu

The Help menu has "Report a Bug…" (Shift+Cmd+B shown). It is added natively by `BugReportMenuChannel` in `MainFlutterWindow.swift` (the main menu is not attached to `NSApp` yet while the window's nib wakes, so it retries for ~2 s; the Help menu is found as the last top-level menu because `NSApp.helpMenu` is not always set) and tells Dart over `app.synctogether/bug_report_menu`. `BugReportShortcut` answers it with source `menu`. AppKit owns the key equivalent on macOS, so the Dart Ctrl/Cmd+Shift+B binding exists only on Windows and Linux (Ctrl+Shift+B); one press can never open the sheet twice. The handler is owner-guarded: a remount builds the new state before disposing the old one, and a plain `setMethodCallHandler(null)` in the old `dispose` silently killed the menu. Windows has no menu bar in this app, so nothing is added there.
