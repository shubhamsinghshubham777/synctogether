# Pairing, Our Room, date nights and push

Read before touching `lib/pairing/`, `supabase/migrations/20261107*`, `supabase/functions/push-dispatch`, the three native `push` channels, or anything that changes how a room is counted, retired or entered.

Two signed-in accounts can **pair**. A pair owns one persistent private room (**Our Room**), date nights, and a history that feeds a weekly streak and a shareable year card. It exists for long-distance couples, but nothing in it says "couple" to the server: it is two accounts and the rules below. Rooms with friends and family are untouched.

## Data model (`20261107100000_pairing.sql`, `20261107110000_pair_features.sql`)

- `pairs`, `pair_members` (**`user_id` is the primary key: one pair per person**), `pair_invites`. All client reads are RLS-gated to the caller's own pair (`my_pair_id()`); **every write is a `security definer` RPC**. Tables grant `select` only.
- Deleting *any* membership deletes the whole pair (trigger `pair_member_removed`), which cascades to the other membership, Our Room, nights and sittings. Account deletion therefore ends the pair for both; `unpair()` announces `room_ended {reason: deleted}` first so a partner standing in the room is ejected.
- **Pairing is account-scoped. Guests cannot pair** (`assert_can_pair` raises `sign_in_required`). `effective_tier` stays the single arbiter, so "guest" is never re-derived client-side.
- `profiles.timezone` is an IANA name written by `set_my_timezone` (validated against `pg_timezone_names`). The partner's clock row is shown **only when it differs from the device's own offset** at that instant (`shouldShowPartnerTime`); DST is read at the moment in question, not today.

## Invites

- 48 h, six characters from the room alphabet, **one pending invite per inviter** (partial unique index); `create_pair_invite` reuses an unexpired one, so "Share again" never mints a second.
- `pair_invites.seen_by` is **not a claim**. It records the last signed-in person who opened the link, and exists only so the lobby banner can remind them after "Not now" or a cold start. Anyone can still accept while it is pending, so a forwarded link cannot lock out the real partner.
- **Invite by email** (`invite_pair_by_email`). The sender types an address; the server makes (or reuses) the invite as usual and, if the address belongs to a signed-in account, sets that account as the invite's `seen_by` (so the lobby banner appears live over realtime) and queues a `pair_request` push. **The answer is identical whether or not an account matched** - it returns the invite and nothing else - because any difference would let anyone test which addresses have accounts, and the UI says only "on its way, if that address has an account". It is rate-limited to **5 addresses per sender per rolling day, matched or not** (`pair_email_invites`), and never matches a guest, the sender, someone already paired, or someone who has blocked the sender - each of those is silent too. The link stays the way to reach someone with no account yet, and a link-only invite still has no push (the invitee is unknown until they open it).
- Accepting cancels both people's other pending invites (no stale codes). The order of refusals in `accept_pair_invite` is deliberate: an invite from someone who has since paired answers `partner_already_paired` ("they paired with someone else") rather than "cancelled", and `get_pair_invite` carries `inviter_paired` so the accept screen says so before offering a button. The same goes for a person who is already paired themselves.
- A typed pair code works in the pair screen's "Got a code from your person?" box and in the lobby's "Enter a code" box: `join_room` says `room_not_found`, and `_openPairInvite` then tries it as an invite. A pair link to a signed-out person is parked in `PairService.pendingPairCode` and consumed after login, like `pendingJoinCode`.
- `synctogether://pair/<code>` is parsed by `pairCodeFromLink` (server alphabet only, so a stray path never reaches an RPC). The web page `/pair/<code>` (`website/app/pair`) reuses `JoinLauncher` with `kind="pair"`; its copy differs because pairing is the one thing that needs an account. It says nothing about the sender: a code is a capability.
- **Names.** An account whose provider shared no name has the email's local part as its display name (Sign in with Apple's hidden address gives a random handle like `68tgy66wnh`), which the other person then reads on the invite and in Our Room. `PairNameCheck` asks "What should your person call you?" on the invite and accept screens when `isGenericName(name, email)` (empty, or equal to the local part, ignoring case), prefilled by `suggestedName(email)` only when the local part reads as a name. It is asked until answered, once per account per device (`pair_name_answered_<id>`); "Keep it" counts as an answer. **Email invites never reach an Apple Hide My Email account** (the address the sender types is not the relay address), which the invite screen says in one line: the link and code are the way in.
- **Notifications are offered where they matter**, not only on the hub (which exists only once paired): `PairPushPrompt` on the invite screen ("a ping the moment they accept" - the accept push cannot reach a first-time inviter otherwise), a one-time dialog right after accepting (`offerPushAfterPairing`), and the quiet hub row. All three ask the OS in place via `turnOnPush`; only a refusal opens the settings screen.

## Our Room - the invariants that are easy to break

Our Room is an ordinary `rooms` row with `pair_id` set (unique per pair), created by `open_our_room()` and restarted by it when resting. What makes it different is in five places, and **adding a sixth place that counts or ages rooms means adding the `pair_id is null` / `pair_id is not null` branch there too**:

1. `create_room` and `resume_room` count live and persistent rooms with `r.pair_id is null`, so Our Room **never uses a room slot** (a free account is `max_live_rooms` 4). These were patched from their *live* definitions (`pg_get_functiondef`), not from the migration files: the latest body of `create_room` lives in `20261006130000`, not where the name is first defined.
2. `room_state` returns `live`/`idle` for a pair room whatever the owner's tier, never `expired`. Without this a free owner's Our Room read `expired` and was swept.
3. `sweep_rooms` skips pair rooms in the "drop persistence for lapsed premium" step and in the idle-TTL delete, and prunes their chat at 90 days.
4. `retire_room` **keeps the chat** of a pair room (the lobby promises "chat history carries over").
5. `join_room` answers `room_not_found` to anyone not in the pair, so a stranger holding the code cannot occupy a live room. `list_my_rooms` excludes pair rooms: Our Room is reached through the pair card, never as a ticket.

**Both partners are hosts.** `set_room_media` is host-only and either partner must be able to choose what plays. Hosts cannot kick one another (`kick_member` refuses), so neither can remove the other, and succession on leave still has a host to fall back on. Presence is read from the room's own channel; "is my person on" comes from private presence on `pair:<pair id>`, authorised by the same `my_pair_id()` rule (`pair_id_from_topic` policies on `realtime.messages`).

**The room screen treats Our Room as what it is** (`room.isOurRoom`): no room-code chip, no Invite button and no "Copy invite link" (nobody else can join it); no "Take the remote" (both are hosts) and no "End for everyone" (it is never deleted, and pause stops the show for both); the menu header reads "THE TWO OF YOU"; the ended dialog says "Our Room is resting" instead of "Room saved"; the sync line reads "WAITING FOR <NAME>" / "TOGETHER"; and the session clock only shows in its last 30 minutes (a countdown on the couple's own room reads like a rental). The ended-dialog Patron offer is shown to a pair with no Patron on either side and to nobody else.

**Guessing a pair code is budgeted.** A pair code is a bearer credential and accepting pairs you at once, so every `get_pair_invite` and `accept_pair_invite` spends from **30 per rolling hour per account** (`pair_code_lookups`, `pair_code_throttle()`), after which they raise `too_many_attempts`. A miss must *return*, never raise: an exception rolls the whole call back, including the row that counted it, so a script guessing blind would never be counted. Hence `get_pair_invite` answers `{status: 'not_found'}` and `accept_pair_invite` returns null for an unknown code, and `PairService` turns both back into `invite_not_found`. The lobby's "type a code in the room box" fallback goes through the same budget and swallows `too_many_attempts` quietly.

## Patron rules

`pair_is_patron(pair)` = **either** partner is premium (via `effective_tier`). It decides two things, enforced in SQL:

- **Creating a date night** raises `patron_required`. Answering, accepting, moving and cancelling one never do - a free partner can always take part in what they were sent.
- **History older than 7 days** is hidden (counted in `locked_count`), never deleted. `pair_history_export()` returns everything on any plan, so a lapse never feels like losing memories.

Booked nights keep their reminders if Patron ends; nothing is removed. The client mirrors these as affordances only (`PairInfo.patron`).

**What one Patron seat covers, and what it deliberately does not.** The room's AV level is the better of the two partners' (so video is shared); date-night creation and the history archive follow `pair_is_patron`. Session length and extension are **per caller**: Our Room always starts at 4 h, and `extend_room` prices the *caller's* own tier, so a free partner cannot extend at all (`free_extension_minutes` is 0 in production, which is the upsell) and a Patron can extend to the 24 h total. The lobby slider's right end says "4 HOURS · EXTEND TO 24 H" for a Patron, since the slider only sets the starting length. The video trial is one per room row (`video_trial_ends_at`), so Our Room gets one 10-minute taste, not a daily one; un-pairing and re-pairing makes a new room, bounded by the per-host daily cap. Pairing is one person to one person, so a seat can carry exactly one other account. The soft prompts for a pair with no Patron are `PairPatronNote` on the hub (surface `pair_hub`) and the ended-dialog offer; neither blocks anything.

## Date nights, history and the streak

`date_nights.proposed_by` is whoever made the *latest* proposal; the other person answers it, so moving a night hands the answer across (`nightStanding`). Reminders are queued for both people 15 minutes ahead under a per-night collapse key (`dn:<id>`), so a move replaces them and a cancel deletes them.

**A date night is a night with the film already waiting** (design: boards 61 and 65 to 67, spec `~/ldr-design-spec.md` Part B). Its planner may attach a YouTube link (`attach_kind`, `youtube_url`; the CHECK keeps the two in step, and `'file'` is reserved for the upload-ahead phase). The server only checks the domain (`is_youtube_url`); the app validates properly with `youtubeVideoId` and always sends the canonical `watch?v=` form. **`open_our_room()` puts the film in the room**: an accepted night whose window is open (15 minutes before to 4 hours after) with `media_applied_at is null`, applied once, and only when that opening starts a session or the room has nothing in it, so it never replaces what the two of them already chose. Only the planner changes the attachment (`set_date_night_attachment`), which also rewrites the reminder so its words match (`schedule_date_night_reminders` says "<title> is ready" or "Pick something together in Our Room."). A failed list fetch is its own state (`PairService.nightsLoaded` / `nightsFailed`, `retryNights`): a skeleton, an empty state and an error are three different screens. On a phone the plan form is a page (`/lobby/pair/plan-night`) with the primary pinned; wider screens get the dialog. The form shows one plain time line when the partners share a clock and the two strips only when they differ. **A night can also carry a file, uploaded ahead** (`attach_kind = 'file'`, migration `20261108110000`). It rides the **same staged-upload slot a lobby pre-upload uses**, so the per-file cap, the weekly allowance (debited at `ready`), the abort penalties and the R2 clean-up all apply unchanged. The sequence: the planner's app calls `staged-initiate` (quota and size are decided here, so a refused file makes no night), then `create_date_night(..., p_staged_id)` **adopts** the slot (`date_night_link_staged`): `staged_media_uploads.date_night_id` links it, its `expires_at` moves from one hour to the night plus a day, and the profile's lobby upload lock is released so a lobby pre-upload started meanwhile does not destroy it. One upload per planner at a time (`upload_in_progress`). The planner's app keeps uploading after the plan form closes (`DateNightUploader`; foreground only, the screen says to keep the app open) and reports progress to the night every ~4 s (`set_date_night_upload_progress`, planner-only, monotonic); both people read `uploadBytes / fileSize`. A trigger on the slot keeps the night in step: `ready` marks the night ready and pushes "Your movie is ready" to the partner (once the night is accepted, so also on accept), `failed` or a deleted slot takes the file off the night. **A dropped connection must not delete the slot**: `uploadStagedFile` normally aborts its own slot on any failure, so a date night passes `keepSlotOnFailure: true` and resumes the same session (`resume:`, which asks `staged-list-parts` and skips the parts the server holds); a cancel still aborts. Resume only works while the app process lives; after a restart the planner picks the file again (`date_night_attach_staged`, which frees the old slot). **When the night starts, Our Room claims the object exactly as `create_room` claims a staged one** (`apply_date_night_media`: the room's R2 columns, `claimed_room_id` on the slot so it is neither swept nor queued for deletion, and the room's session end queues it through `retire_room` as usual). It runs from `open_our_room()` and, when the file lands while the night is on and the room is live and empty, from the ready trigger. **The server also sends `media_set` (and `upload_progress` `ready` for a file) on `room:<id>`**, because members adopt a media change from that broadcast and nothing else tells a partner already inside; this fixed the same gap for YouTube nights. A cancelled night frees its file at once (`free_date_night_file`); an unused one is freed a day after the night (`sweep_date_night_files` in `minutely_maintenance`); a pair ending deletes it with the night. `clear_staged_upload` no longer counts a *ready* date-night slot as an abort (the expiry sweep calls it). **The 15-minute reminder reads the night when it is sent**: `claim_push_batch` rewrites a `date_night_reminder` body through `date_night_reminder_body`, so it says "ready", "still arriving (84%)" or "pick something together" as things stand then, not as they stood when it was queued. The file cannot be added to a night after planning from the Change dialog (only link or none); choosing again after a stop is the stopped card's "Try again". Not built: the per-night reminder toggles on board 61, which the design calls existing but the product never had, and background upload on iOS.

**Add to Calendar is the system's own sheet** (`calendar_bridge.dart`, channel `app.synctogether/calendar`): iOS presents EventKitUI's event editor, Android launches the calendar app's insert screen, and neither lets this app read a calendar. On iOS 17+ the editor runs out of process and needs **no permission**; on iOS 15-16 (the current deployment target is 15.6) it needs calendar access, requested only at that moment, and a refusal falls back like desktop. Desktop and any refusal answer `unsupported`, and the screen shares a calendar file instead (`buildDateNightIcs`: start in UTC, a 15-minute alarm). Raising the iOS floor to 17 would let the permission branch and the two `Info.plist` calendar strings go.

`pair_sessions` is written by `log_pair_session` and is **idempotent per minute of start**: both partners report the same sitting and the longer report wins. The room feeds a `TogetherClock` that runs only while both are present (`_trackTogether`), writes when the partner drops out (so a killed app costs minutes, not the night) and once more on exit. A week counts toward the streak at 20+ minutes together; the current streak survives an unfinished week. The year card is stats only (no titles, no chat) and is drawn at one fixed size with text scaling off, so it looks the same for whoever shares it.

## Push

The database decides **what to tell whom and when**; `supabase/functions/push-dispatch` only delivers.

- `push_tokens` (per platform, with APNs `environment`), `push_prefs`, `push_outbox`. Clients reach them only through RPCs; the outbox and tokens are unreadable even to their owner.
- `enqueue_push` queues nothing for a person with no device and respects their switches; a **collapse key** replaces an unsent row (`dn:<id>`, `wl:<pair>`, `reunion:…`).
- **Quiet hours are enforced at claim time, in the recipient's own zone** (`claim_push_batch`: 23:00-08:00 holds everything except `kind = 'call'`), so a reminder queued at noon still respects 11 PM. A call expires in 90 s and is throttled to one a minute.
- `invoke_push_dispatch` is `invoke_r2_cleanup`'s twin: inert until `app_settings.push.endpoint_url` is set, then `pg_net` from `minutely_maintenance` and straight after an enqueue.
- Providers are independent and optional (`_shared/push.ts`, 12 Deno tests): APNs over HTTP/2 with an ES256 provider token, FCM HTTP v1 with a service-account OAuth token, WNS with client credentials. An unconfigured platform is **skipped, never failed**, so a fork shipping on one platform needs only that platform's secrets. Dead tokens (APNs 410, FCM `UNREGISTERED`, WNS 404/410) are dropped. **WNS channel URIs come from clients, so only `*.notify.windows.com` is ever called** (`isWnsChannel`).
- **Order of go-live matters.** A row for a platform whose credentials are not set is *skipped and completed*, not retried (so an unconfigured platform cannot clog the queue). Set the provider secrets **before** `app_settings.push.endpoint_url`; flipping the endpoint first consumes any queued pushes without delivering them. Production state as of the pairing rollout: migrations and `push-dispatch` deployed, APNs and FCM secrets set and the endpoint switched on; **WNS secrets are not set yet**, so a Windows token would be skipped until they are (none can exist before a Windows build with push ships).
- Reliability: an alert push is shown by iOS/macOS/Android even after a swipe-away; **force-stop** on Android and silent pushes after a force-quit on Apple are not delivered by any server design, which is why nothing here relies on silent pushes.

Client: one `MethodChannel` (`app.synctogether/push`) answered by every runner, so `PushService` is a single Dart implementation tested against a fake `PushBridge`.

- **Nothing prompts by itself.** `start()` only reads the permission; `enable()` is the one call that shows the OS prompt, and it runs because a person just turned a switch on (notification settings, or the hub's "Hear it when Sam calls").
- iOS/macOS: APNs directly, no SDK. A debug build's token is `sandbox`, a release build's `production`. The macOS `aps-environment` entitlement is **only in `Release-Store.entitlements`**: a restricted entitlement on a build without a provisioning profile makes AMFI kill the app at launch, so local debug builds simply have no push.
- Android: FCM with **no `google-services` file**. Firebase options arrive as `--dart-define`s (`Env.firebaseOptions`, all four or none), are stored by `Push.configure`, and `App.onCreate` re-initialises Firebase from them so a message can start a cold process. Unset, the build reports `unsupported` and offers no switches.
- Windows: WNS needs package identity, so only the packaged MSIX build has push. A toast is written with **protocol activation**, so a tap launches `synctogether://push?route=…` and the existing `app_links` handler does the rest - there is no native tap code. **`push_channel.cpp` was written without a Windows toolchain and has not been built or run**: build it, then test a real toast on a packaged, Store-associated install before relying on it (the same caveat `store_purchase.cpp` carried until it was exercised).
- Sign-out calls `PushService.forgetDevice()` *before* the session goes, because afterwards the server can no longer be told to stop pushing that account to this device.

## Testing seams

`FakePairService` (`test/support`) hands a screen its state with no backend; `test/layout/pair_matrix_test.dart` and `pair_screens_matrix_test.dart` run every pair screen across the whole screen matrix (folds, iPhone Duo, 2x text) and write real-font PNGs with `--dart-define=SCREENSHOTS=true`. Decisions are free functions in `pair_logic.dart`, `pair_links.dart`, all unit tested. `supabase/tests/30_pairing_test.sql` and `31_pair_features_test.sql` cover the RPCs; the second runs row-visibility assertions **as the `authenticated` role** (a superuser bypasses RLS and would pass for the wrong reason).

## Analytics

Product events fire only where a human caused them: `pair_invite_created`, `pair_invite_shared {via}`, `pair_invite_emailed`, `pair_accepted`, `pair_ended`, `our_room_opened`, `partner_called`, `date_night_planned`, `date_night_answered {accepted}`, `pair_year_shared`, `push_enabled {platform}`, plus the existing `upgrade_cta_shown/clicked` with surfaces `date_night`, `pair_history` and `pair_hub`. Never a film title, a link, a name or chat. All are listed in `lib/analytics_catalog.dart`, which a test keeps in step with the code.

## Not built (decided, not forgotten)

A shared watchlist and "Pick tonight" were built and then removed. This app plays the pair's own files and YouTube links, so there is no catalogue to recommend from, and a bare list of typed titles did not earn its place. If it comes back it should start from a real need (a title that reaches the room's source picker), not from a list.

A QR code for the invite (a long-distance pair is rarely in the same room, and the share sheet, link, code and email already cover it); "ping me when Sam is on"; a per-week breakdown behind the streak dots; hours-and-days granularity on the reunion card (the reunion is a calendar date with no time).
