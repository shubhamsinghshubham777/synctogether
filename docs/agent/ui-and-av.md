# Layouts, room UX, subtitles, chat emoji, AV and analytics

Layouts, room UX, subtitles, chat emoji, AV and analytics: read before touching lib/ui/, RoomScreen, lib/player/, lib/av/ or Analytics.track.

## Responsive layouts (`lib/ui/responsive.dart`, `test/layout/`)

- **Layout is two questions, not a width.** `layoutOf` combines size with `inputOf` (pointer on the desktop targets, touch everywhere else): pointer windows >= 840 wide are `desktop`; touch windows whose shortest side is >= 600 are `tablet`; everything else is `landscape`/`portrait` by aspect. Width alone put iPads on the mouse-first desktop layout (hover-reveal, cursor hiding, no skip zones) and iPad minis on a stretched phone one. `classifyLayout` is the pure form and `test/ui/responsive_test.dart` pins it as a device table. The window size is what is classified, so an iPad in 1/3 Split View is correctly a phone.
- **`PTResponsive` falls back tablet → desktop → landscape → portrait.** Most screens need no tablet builder of their own; the room does (`_tablet()`: the roomy composition with touch input, or video-over-content in portrait).
- **The desktop room is one docked composition at every window size** (`_theater()` -> `RoomTheaterLayout`). Nothing floats over the picture: a full-width 52 px `CinemaMarqueeBar` across the top, then a row of [picture over a flat `RoomControlBar(docked: true)`] beside chat as a full-height Seat column (`kTheaterChatShare` of the window, 280-`kTheaterChatWidth` px, so the 900x600 minimum still leaves the picture most of the width) with an "IN THE ROOM" roster of `ReadyRing`s. **The marquee bar is the window's title bar**: the native one is hidden, so it carries the macOS traffic lights (`MainFlutterWindow.placeTrafficLights` pins them to its vertical centre line - AppKit would centre them in *its* title bar height, off the header's - and re-applies on resize, focus and fullscreen exit) or, on Windows, the min/max/close buttons, and doubles as the drag area. It never collapses in a window. Fullscreen has no window controls, so there H or a click on the picture collapses the header and the control bar together (`_collapsible`: the picture grows into the slot, nothing slides over it); in a window the same gesture collapses only the control bar. Idle never hides anything. The header carries back, name, code tag, sync dot + label, "house lights in ...", Invite, chat and the menu, stepping pieces out as the bar narrows - never wrapping. The bars follow their boards (04 / 08): typed `−10`/`+10` keys, `SUBS · EN`/`AUDIO · JA 5.1` keys that name the selected track (`shortTrackTag`), no source or file key - those, keyboard shortcuts and the audio track live in the room menu (`_menuPlaybackActions`); mic/camera/output device choice rides a right-click or long-press. The sync label's `±0.2s` is `SyncService.measuredDrift`, real heartbeat data that falls back to the seat count for the authority. The docked bar's far-side group (SUBS, AUDIO, volume, then More) is an `AdaptiveActionBar`: when the row runs short AUDIO folds into the bar's More list, then SUBS, then the volume, and the slider drops to the glyph below 820 px - nothing is ever scaled with a `FittedBox`. `_controlsOverVideo` is false on desktop, so there is no control scrim there. The floating "roomy" composition (`_roomy`) is now touch tablets' landscape only; phone portrait uses the same flat bar, full-bleed under the video.
- **Folds come from `foldOf` (`MediaQuery.displayFeaturesOf`), never a device model.** Only a hinge or a half-opened fold splits; a flat fold is a continuous display. The room renders `_folded()` for a split touch window: book posture puts video left and chat right, tabletop puts video in the top pane and the transport in the bottom one. Nothing interactive may straddle the hinge rect.
- **A layout-class change must not remount the video.** Split View drags and fold/unfold cross classes mid-session; the video surface sits under a `GlobalKey`'d `KeyedSubtree` so the YouTube platform view moves rather than rebuilding, which would restart playback. The embed stays keyed by `ObjectKey(controller)`. **The chat panel is deliberately not keyed**: its composer owns an `OverlayPortal` (the emoji popover), and reparenting that subtree across layouts throws `overlay.dart: _attachTarget == this` / `framework.dart: _elements.contains(element)` and replaces the whole panel with a red error box. It remounts instead, and the half-typed message survives because `RoomScreen` owns the draft (`_chatDraft`, passed as `RoomChatPanel.draftController`). `room_screen_controls_test.dart` ("layout transitions with chat open") pins this; do not re-add the key.
- **Dialogs size themselves to the screen.** `showGlassDialog` treats `width` as a cap inside a 16 px gutter, stops above the keyboard, scrolls its body by default (`scrollable: false` for a dialog that manages its own list - an inner `Expanded`/`Flexible` under the default scroll is unbounded), and `sheetOnCompact: true` presents long forms as a bottom sheet under 480 wide.
- **Text scales up to 2x and no further** (`MediaQuery.withClampedTextScaling` in `MainApp.builder`). Labels ellipsize or wrap, never overflow; icon-only controls do not scale. Touch layouts give `PTIconButton`/`PTButton` a 44 pt hit area without changing their visual size; pointer layouts are untouched.
- **Edge-to-edge, with insets consumed where content is, not where backgrounds are.** Mobile runs `SystemUiMode.edgeToEdge` with `kSystemUiStyle` (`lib/ui/system_ui.dart`: transparent bars, light icons, contrast enforcement off), applied through an `AnnotatedRegion` in `MainApp.builder` so nothing overwrites it. Scroll views use `SafeArea(bottom: false)` plus the bottom inset in their padding, so a list runs under the nav bar but its last item is reachable; full-bleed video, scrims and backgrounds sit under insets on purpose. The launch windows on both platforms are `PTColors.canvas` - they were white, which flashed before every cold start in light mode. Phone landscape goes `immersiveSticky` only while playing with controls hidden, and every exit path (controls shown, pause, leave, `dispose`) restores edge-to-edge.
- **Collapse, don't wrap.** A header or action row that runs out of room must step down to a smaller *designed* form, never `Wrap` into a stack - wrapping passes every overflow test and looks broken (the lobby header once wrapped its chips into a column on phones and dropped logout onto its own line at ~1000 px). The lobby header uses `FirstFit` (`lib/rooms/widgets/lobby_header.dart`), which measures each candidate row at its natural width and shows the first that fits: full pills → compact chips → items folded into the avatar's account menu. Dialogs use `PTButtonBar` (side by side while every label fits one line, stacked otherwise) and `GlassDialogHeader`; dialog titles scale at half the body rate (`dialogHeadingScaler`). `PTButton` answers intrinsic sizes itself, because the lobby and login measure it under `IntrinsicHeight` and a bare `LayoutBuilder` throws there.
- **The phone and tablet control bar collapse through a ladder of forms, never by scaling** (`room_bar_form.dart`, board 46). Seek bar (with both time labels) and play/pause are in every form; only the icons beside them fold, into one More button (`room_bar_more.dart`, a `showPTPopover` list of the folded rows - same `AdaptiveAction` data as `AdaptiveActionBar`, drawn the board's way: 44 px cells, value under the name, two columns past five rows, anchored above the button). F1 two rows (112 tall) -> F2 one row (hide, source, file, audio, subs and the skips fold) -> F3 (react) -> F4 (camera) -> F5 (mic; seek, play, More) at 552/484/436/388/332 px; the touch tablet's floating bar goes T0 (SUBS key + volume slider) -> T1 (slider folds to the glyph) -> F3-F5. `pickBarForm` takes the first form whose *measured* width fits (the labels grow to 1.3x text, so larger text steps down earlier; a bar with no mic/camera fits sooner). Height is the second input: in phone landscape the layout picks the form with the facecam rail in mind (`railPlanFor`: the slot from y=72 to the bar top minus 12 must hold two tiles plus +N; 136x77 tiles from 210 px, else 104x58) and hands it down through `RoomBarFormScope`; the bar still takes the narrower of that and what its real width allows, so an animating slot never asks a form for room it has not got. The chat column is `min(300, 38%, safe - 12 - 332)` (never under 180), the rail sits left of it (`chat + 12`), and a window too short for the chat's text gives the chat the whole column while the bar stays beside it - only the soft keyboard, or a safe width under 524, lets chat take the bar's slot. Portrait is `RoomPortraitStack`, which spends height in priority order (header, bar, reaction strip, picture, roster strip, banners) with the chat floor measured at <= 1.3x text, so the transport can never be scrolled or squeezed away; a roster or reaction strip that does not fit whole is hidden, not clipped.
- **Touch has no hover.** Anything a pointer layout reveals on hover (chat bubble copy/report) is revealed by a tap on touch - never shown permanently, which reads as clutter beside every row.
- **Look at it, don't just test it.** `fvm flutter test test/layout --dart-define=SCREENSHOTS=true` writes a PNG of every matrix case at 1.0x and 2.0x to `build/screenshots/`, rendered with the real fonts (the matrix always loads them - Ahem's square glyphs hid real overflows). BoxShadows render as hard unblurred blocks in `flutter_tester`; that is the renderer, not the app. A layout change is not done until its screenshots have been looked at.
- **`RoomScreen(dependencies:)` exists only so the room is testable** - `RoomDependencies.videoView` replaces media_kit's `Video`, and when set no `VideoController` (native libmpv, absent under `flutter test`) is created. It defaults to `RoomDependencies.real`; keep it pure delegation, like `SyncBackend`.
- **`test/layout/` is the definition of "supported".** It renders every screen and dialog over `kScreenMatrix` (phones, landscape with keyboard, iPads, Split View, foldables, desktop minimum to ultrawide) at 1.0/1.5/2.0 text and fails on any overflow, and on any tappable control or focused field that sits under a system inset or the keyboard (`expectRespectsInsets`). A new screen or dialog must be added to it.

## Room viewing UX (`RoomScreen` + `room_control_bar.dart`)

- **Keyboard/focus**: shortcuts are ignored while any `EditableText` has focus. Esc consumers are strictly ordered - emoji picker close (consumed inside `RoomChatPanel`, which leaves the field focused) → text-field unfocus → reaction strip close → chat close → fullscreen exit - and new Esc handlers must slot into that order explicitly; whatever closes must hand focus back to `_shortcutFocus`.
- **Desktop single-tap on the video is intentionally instant**: no `onDoubleTap` on that gesture detector (double-tap recognition adds ~300 ms lag; a deliberate product call). Touch layouts get double-tap ±10 s skip zones instead; double-click-fullscreen was rejected for the same reason - fullscreen is F/Esc via `window_manager` (desktop only, gated by `lib/platform.dart`; a `WindowListener` keeps the flag synced with native green-button transitions).
- **Panel motion**: `GlassPanel` no longer blurs, so fading one is safe now; the existing slide/clip animations (the chat panel's `_chatAnim`) are kept because they read as mechanical, which is the projection booth cinema motion language. A collapsed overlay in a `Positioned` still fills its slot (tight constraints) and eats clicks - wrap the zero state in `IgnorePointer`.
- **Broadcast on gesture end, preview locally during** (scrub `_dragValue` pattern) - never broadcast per-tick.

## Local video chooser (`lib/player/local_video_chooser.dart`, board 47)

- **Every "pick a video from this device" button opens one chooser** (`showLocalVideoChooser`): the room's `_pickVideo` (empty-state Choose a video, Locate copy, Open file, Switch source, Pick another), the lobby's staged upload and the tablet empty room's own Photos/Files keys (`autoStart:`). It returns a ready `LocalVideo` and the **caller owns `release()`** and recording: `RoomScreen._adoptLocalVideo` plays, releases the previous handle, writes `LocalMediaStore` (with `reference:`) and `RecentVideos`, and `dispose`/`_leaveRoom` release the last one. Sharing and uploads go through `video.uploadSource()`, so an Android `content://` pick works with no path; `entry.reopen()` replaces `File(entry.path)` for per-room auto-reopen.
- **Form follows the layout class**: bottom sheet under 480 wide (stacked rows), dialog with side-by-side tiles on a tablet, Files-only on desktop (`showPhotos` is `photosAvailable`: iOS and Android), and a two-pane panel in phone landscape (`height < 500`) whose shelf scrolls on its own only while the whole panel fits - with a keyboard, a gesture bar or text past 1.15x it is one scroll, because a scroller half hidden by an outer scroll fails the inset check. Entry titles scale at the dialog-heading half rate so "From Photos" never folds on a 320 pt phone at 2x.
- **From Photos is a native picker, not a package.** `image_picker` was rejected because its iOS half calls `PHPhotoLibrary` authorization APIs, which makes App Store Connect demand `NSPhotoLibraryUsageDescription` even if never used. `PhotoPickerChannel` (AppDelegate.swift, `PHPickerViewController`, out of process, exports the movie once into `tmp/PhotosPicks`) and `PhotoPicker.kt` (`ACTION_PICK_IMAGES`, `ACTION_GET_CONTENT` fallback, a temporary `content://` grant) need no permission and no usage string. Photos picks are `VideoOrigin.photos`, so Recent declines them.
- **Recent rows learn they are unavailable by being tapped** (a stat or bookmark resolve), except plain paths on desktop, which are probed with `File.existsSync` when the shelf loads. Probing a bookmark or content URI would start access that nobody releases. Locate replaces the stale entry rather than adding a second one.
- **Analytics**: `local_video_chosen {source}` (photos/files/recent) fires from the chooser's own success edge and from the empty room's Reopen line, never from a remote path.

## Subtitles (`lib/player/subtitles/`, `lib/player/video_surface.dart`)

- **libass renders subtitles on every platform, and the Flutter `SubtitleView` must stay off** (`visible: false`). The Flutter view only receives plain text from mpv, so ASS/SSA styling and older files' tracks came out unstyled or blank - that is why libass was adopted, and why it is not a desktop-only choice. Android's libass cannot see system fonts at all, so the Player passes `assets/subfont.ttf` (Droid Sans Fallback) as `libassAndroidFont`; without it Android draws no subtitles.
- **mpv is 0.36 on macOS/iOS/Android and 0.41 on Windows** (see Codec support). `toMpvProperties` must therefore work on both: it keeps the old `sub-border-*` names (0.41 still accepts them; `sub-outline-*` would silently no-op on 0.36), pins `sub-font-size` to 55 (0.41's default is 38, ~31% smaller text), and writes `sub-border-style` (0.41 needs it for the background box; 0.36 ignores the key). **Any new mpv property we depend on has to be pinned explicitly for the same reason.** `subtitle_style_test.dart` pins the mapping.
- **Style is a per-device viewer convenience**: `SubtitlePrefs` (shared_preferences `pt.subtitles.style`), the `EmojiPrefs` shape, cleared in `signOut`/`deleteAccount`. `SubtitleStyleApplier` (one per room Player) writes only changed keys, live on every change (a slider drag moves the subtitles as it goes; ticks during an in-flight write coalesce into one write of the latest style, while disk persistence still waits for the drag end); mpv keeps these options across `open()`, so nothing re-applies per file.
- **libass knows bold on/off only, so weight picks a *face*.** `SystemFonts` lists each family's faces over the `app.synctogether/system_fonts` channel (macOS `NSFontManager` / iOS `UIFont` PostScript names, Windows DirectWrite full names in `windows/runner/system_fonts.cpp` - libass matches both directly); `resolveFace` picks the nearest, and `sub-bold`/`sub-italic` synthesise only what that face lacks. Android parses `/system/etc/fonts.xml`, copies the chosen file into a `sub-fonts-dir` of our own beside the bundled fallback, asks libass for it by the name *inside* the file (`readFontNames`), and toggles `sid` because the fonts dir is only read when a track initialises.
- **`sub-blur` blurs outline and shadow together** - libass has no shadow-only blur, and the sheet says so. `overrideEmbedded` maps to `sub-ass-override=force`; off is `scale`, which keeps ASS typesetting (signs, karaoke) intact.
- **Sharpness comes from the render texture, not libass.** mpv draws subtitles into its texture, which media_kit sizes to the *video* by default - a 720p file on a Retina screen rasterised its text at 720p and Flutter stretched it. `VideoSurfaceSizer` keeps the texture at the on-screen physical size (`renderSurfaceSize`: contained, capped at 4K, even, debounced), and `applyVideoQualityOptions` sets spline36 scalers. Keep `blend-subtitles` at its default `no`, or subtitles go back to video resolution. **Android is excluded** (media_kit resets its surface to the video size on every video-params event and `setSize` throws there) - soft subtitles on Android are accepted for now.
- **Picture subtitles (PGS, VobSub, DVB, XSUB) cannot be styled** - the look is in the pixels. `isBitmapSubtitle` (`track_label.dart`, by mpv codec name) labels them "Picture" in the chooser, which explains why. mpv auto-selects the *first* track in the preferred language, which on a Blu-ray rip is usually PGS, so `_preferTextSubtitleOnOpen` swaps to a same-language text track (`preferredTextSubtitle`; forced/signs-only tracks lose to full ones) once per **fresh** open. It must not run on the 403 re-sign reopen, which restores the viewer's own choice, even if that is a picture track.
- **iOS decodes 10-bit/HDR through the copy path, not zero-copy.** media_kit_video on iOS renders through a GL ES `TextureHW` with `hwdec=auto` = `videotoolbox` zero-copy; iPhone camera clips are 10-bit Rec.2020 HLG (`p010`), which that interop is believed to mis-sample (green/magenta tint, diagonal bands seen on a real iPhone, camera-roll clip). `planVideoPath` (`lib/player/video_color_path.dart`) is the pure decision and `VideoColorGuard` (attached from `applyVideoQualityOptions`) applies `hwdec=videotoolbox-copy` + `vf=format=nv12` to streams above 8-bit or with an HLG/PQ/log transfer, and resets on the next file; 8-bit SDR keeps zero-copy. **This fix is built from the code path: the iOS simulator renders in software (`TextureSW`) and cannot reproduce the bug, so only a real iPhone confirms it.** `--dart-define=MPV_HWDEC=<auto|videotoolbox|videotoolbox-copy|no>` forces a mode on iOS for comparison (`tool/hdr_probe/main.dart` dumps mpv's view of a stream). Rotated portrait clips crash the *simulator's* software path (`mp_image_crop` assertion) - not a device finding.
- **Nothing may be painted over the video where subtitles sit.** libass draws them *into* the frame, so every Flutter layer above the video paints over the subtitles too. The old full-height radial control scrim, darkest exactly at bottom-centre, dimmed centred lines ~37% while left/right-aligned ones stayed white. The scrim is now a `kControlScrimHeight` band behind the controls that fades out with them. **Wherever a bar still floats over the picture (touch landscape, folded tabletop; never the docked desktop theatre), while it shows the subtitles also rise out from behind it**: `RoomScreen._liftSubtitles` hands `SubtitleStyleApplier.setLift` the bar's height (`kSubtitleLiftPx`) as a percent of the real picture height, and `liftedSubPosition` subtracts it from `sub-pos` (lower-half lines only, never above the middle). It is layered over the viewer's `position` and never written to `SubtitlePrefs`, so it cannot fight the slider; in-flow layouts, where nothing floats over the picture, reset it to 0.
- **YouTube captions are out of scope**: they are drawn inside the IFrame, which exposes no styling. The style sheet is reachable only from the local-file Subtitles chooser.
- **The style sheet does not dim the video** (`showGlassDialog(dimBackground: false)`, docked to the end edge): the live video is the real preview, `SubtitlePreview` only a Flutter approximation for moments with no line on screen.

## Chat emoji (`lib/rooms/emoji/`, `emoji_picker.dart`, `emoji_quick_bar.dart`)

A full picker beside the chat field plus a seven-slot quick bar above it, spanning the text field's width (not the send button's). Chat emoji are plain Unicode text - nothing about the wire, the `messages` row or the receive side changes.

- **Glyphs come from the platform's own colour font, and nothing is bundled.** Apple Color Emoji is proprietary and licensed for Apple devices only - the apps that ship it everywhere (Telegram Desktop/Web, via `emoji-datasource-apple`) do so unlicensed, and a Mac App Store app is the wrong place to bet on Apple's tolerance. `PTText.emoji` names each OS's font in `fontFamilyFallback`. The price is that a message looks different on each platform, which is how every system-emoji app behaves. If one look everywhere is ever wanted, the licence-safe path is Fluent Emoji 3D (MIT) as a *display* layer over the same text - not a font swap, and the field would still show system glyphs.
- **The picker hides what the OS font cannot draw.** `emojiVersionCap` maps OS + version to the highest Emoji version its font carries (Windows keys on the build number; Android has nothing to key on and sits at 13.1), and `emojiFlagsSupported` drops the Flags group on Windows, whose font has no flag glyphs at all. Received messages are never filtered - what the sender typed is what it is.
- **`maxLength` is gone from the chat field, deliberately.** It counts graphemes; `messages.content` is `char_length(...) <= 500`, which counts codepoints. 👩🏽‍💻 is one grapheme and four codepoints, so an emoji-heavy message passed the field and bounced off the insert. `_CodepointLimitFormatter` and `insertEmoji` both count runes against `kChatMaxCodepoints` (`chatLengthOk` in `sync_logic.dart`), refuse an overshoot whole rather than truncating inside a ZWJ sequence, and a counter appears past 450.
- **Skin-tone variants are folded into their base** by the generator: one cell, five uniform variants in `tones`, offered on long-press / right-click, plus a remembered default tone. Mixed-tone sequences are dropped - one remembered tone cannot reach them.
- **Opening: hover-intent on pointer, tap on touch.** Pointer opens after `kEmojiHoverOpenDelay` (250 ms, so sweeping past the button to the field does not pop it), closes `kEmojiHoverCloseDelay` (300 ms) after leaving both button and popover (the diagonal-move grace), and a *click* pins it open until Esc, an outside click, the button or a send. A hover-opened picker never takes focus, so typing carries on. Ctrl/Cmd+E toggles. Touch swaps the soft keyboard for an inline picker at the keyboard's last height (read from the `View`, because the Scaffold strips insets from what the panel inherits); tapping the field swaps back.
- **The popover uses `OverlayPortal.overlayChildLayoutBuilder`, not `CompositedTransformFollower`.** The follower's paint transform is only known after layout, and anything inside that asks for it during layout (tooltips do) asserts. The layout builder also lets it clamp to the window, which a follower cannot.
- **The quick bar inserts, it never sends** - a slot next to the field must not fire a message mid-sentence. Slots are: pinned first, exactly where put; then usage by score, where a *sent* emoji earns +1 and halves every `kEmojiUsageHalfLife` (14 days); then `kDefaultQuickEmoji` with the remembered tone. **It is a snapshot** (`EmojiPrefs.quickSlots()`), taken when the panel mounts and after a send - never while the pointer is on it, or a slot slides out from under a tap. It gives way before the field does: it needs 300 px of panel (more at larger text scales) and shows fewer slots in a narrow one.
- **`EmojiPrefs` is shared_preferences, per device, and cleared in `AuthService.signOut`/`deleteAccount`** beside the other per-account caches - a second account on the machine must not inherit the first one's favourites. A viewer convenience: failures report and fall back to defaults.
- **No analytics, no tier gating.** Chat is free on every tier and so is everything that types into it.
- **One to three emoji alone render at 34 px without a bubble** (`isEmojiOnly`, over the generated set rather than a regex).

## AV layer (`lib/av/`)

`LiveKitService` (per room): fetches a token from the `livekit-token` edge function, connects to `LIVEKIT_URL`, publishes mic/cam on toggle. Facecam tiles: `lib/rooms/widgets/facecam_rail.dart` (identity = Supabase user id).

**Endpoints are plural, the protocol is not.** The token function holds a priority list of LiveKit-protocol servers (`LIVEKIT_ENDPOINTS`: self-hosted first, LiveKit Cloud behind it) and `pick_av_endpoint` pins each room to one. Members on different SFUs cannot hear each other, so a room moves as a whole: the client that hit the failure re-pins it, and Postgres broadcasts `av_endpoint_changed` so connected members `followEndpoint`. Failover decisions are pure functions in `lib/av/av_failover.dart`. `NotAllowed` (how a free LiveKit Cloud project answers once its hard cap is spent) moves at once. An SFU that won't answer while our token fetch just worked moves after 2 failures. Marking an endpoint down globally needs 2 distinct reporters, so one bad network cannot take AV off everyone. When all endpoints are out the state is `AvConnectionState.unavailable`: traced not reported, slow retry, and the rail's "taking a breather" note instead of an error. The switch itself happens inside `connecting`, so to the user it is a spinner on their own tile. **Do not add a second vendor SDK behind this seam** (Agora, Daily, 100ms, RealtimeKit): members on two vendors cannot hear each other, so a room has to move as a whole anyway, and most of those SDKs have no Flutter desktop support. Every room-facing type (`facecam_rail.dart`, the device pickers, `macos_audio_devices.dart`) is LiveKit's. A new endpoint is a new LiveKit server, never a new protocol. **Moves are make-before-break** (`_connectRoom` swaps the new `lk.Room` in only once it is connected, and listeners ignore any room that isn't `_room`), so a failover or a followed move never leaves `connected`. **The SFU side is cleaned up like ours**: triggers queue `pending_av_cleanups` on end/retire/delete (whole room) and on any `room_members` delete (participant). `av-cleanup` applies each one to *every* endpoint, because a room may have lived on several. Tokens are 10-minute because removal cannot revoke one. Debug switching is `AV_DEBUG_SWITCHING` on the function plus the debug-only room-menu entry.

Facecams are enabled with a single member present: publishing into an empty room gives you your own preview tile while you wait, which is the normal way to check a mic before people arrive, and the old `_present.length >= 2` guard left a lone member with no way to test either device.

**An unreachable AV backend is traced, not reported, until it has stayed unreachable for `kAvReportAfterAttempts` (5) tries.** The reconnect backoff never gives up, so reporting every attempt turned one offline user - or a local stack without `supabase functions serve` (which answers `503 name resolution failed`) - into a flood of Sentry errors. `isTransientAvError` decides: 5xx/408/429/status-0 function errors, sockets, timeouts and non-`NotAllowed` LiveKit connect errors are transient; a 4xx from `livekit-token` or the SFU refusing the token is a real answer and is reported at once.

Availability is `LiveKitService.isAvailableFor(room.avLevel)`, **not** `isConfigured` - a room whose tier grants `av_level: none` reuses the unset-`LIVEKIT_URL` path exactly (no service, no token fetch, no UI), so there is one hiding mechanism rather than two. `voice` keeps the mic and drops the camera toggle (`RoomControlBar.camAvailable`); `video` publishes capped at 360p/24fps, since a rail of up to 16 tiles is a thumbnail grid and the bandwidth belongs to what everyone came to watch.

## Analytics (`lib/analytics.dart`)

Product analytics to PostHog Cloud, so activation/retention/engagement and premium demand can be read off PostHog's built-in funnels rather than hand-built SQL. Configured-or-no-op like `lib/diagnostics.dart`: without `POSTHOG_API_KEY` there is no timer, no socket and no queue.

- **Deliberately not `posthog_flutter`.** That package has no reliable Windows support and Windows is a first-class release platform here; the HTTP API is ~100 lines of `dart:io` `HttpClient`, works on every target, keeps pubspec's exact pins untouched, and inherits `installTlsOverrides`' roots for free. Firebase Analytics (no desktop) and a hand-rolled Supabase events table (no ready-made funnel/retention UI) were both rejected - revisit only if the 1M events/mo free tier is exceeded.
- **Events are user-initiated only, and this is the invariant most likely to be broken by a well-meaning edit.** Never track inside `onRemote*` callbacks, gate-derived actions (`reason: 'gate'`), drift correction, `state_response`, or reconnect paths - eight clients would each report the same room action and every count would be multiplied by room size. It is the same distinction `SyncService.remoteActions` enforces for attribution toasts. Concretely: `media_selected` lives in `RoomScreen._handleModeSwitch`, **not** in `_switchToYouTubeMode`/`_switchToLocalMode`, because the remote `mode_switch` handler goes through those two. They keep only the per-client `_modesUsed` counter and the `playback_started` dedupe reset.
- **No ticks**, mirroring the `trace` rule: nothing per-frame, per-heartbeat, per-presence-sync, per-typing, per-scrub.
- **Privacy is a hard boundary.** Never send chat content, file names, file paths or YouTube URLs/ids. Media is reported as `kind` only. Room ids and user ids are fine. YouTube video ids were considered and deliberately excluded - ask the owner before adding them.
- **Failures are swallowed, always.** Analytics must never break the app it measures, so `flush` catches everything, re-queues the failed batch, and drops oldest past 500. A *persistent* delivery failure earns one `trace(category: 'analytics')` - never `reportNonFatal`, which would make a flaky network look like a bug.
- **`Analytics` is constructible (`Analytics()`) with a `static final instance`** so tests build their own rather than resetting a singleton, and `init` takes the key/host as *arguments* instead of reading `Env`, keeping the `Env` read in `main.dart`. `init` also accepts a transport function, which is what lets `test/analytics_test.dart` cover batching, thresholds and retry without a socket.
- **Signed-out runs start on an anonymous distinct_id and alias via `$identify`/`$anon_distinct_id`.** Without that every signed-out `app_opened` would share one distinct_id and activation would read as a single person. A cold start that already has a Supabase session passes the real user id into `init` and never aliases.
- **Delivery is best-effort by design** - a 30 s timer or 20 queued events, plus a flush on `paused`/`hidden`/`detached` (desktop may never deliver `detached`). `onUpdaterBeforeQuitForUpdate` flushes with a **2 s cap** before `exit(0)`: that immediate exit is what stops the installer racing a live exe, so the queue only ever gets a bounded moment.
- **`achievement_unlocked` is the single render allowed to emit a product event, and the exception is narrow.** By the letter of the doctrine it is a render, like a crown - nobody caused it at that moment. It is permitted because, unlike a crown, it is a discrete, server-authoritative, once-ever fact, and because `UnlockLog` (shared_preferences) dedupes it per badge so a reconnect, a reinstall or a second device cannot inflate the funnel. It fires from the account owner's own toast, never from an observer watching somebody else's unlock, and `UnlockLog.clear()` runs on sign-out and account deletion so a second account on the machine does not inherit the first one's announcements. Do not add a second exception without the same three properties.
- **Reward events** are `recap_shown` / `recap_shared {surface}` / `recap_deleted {views}` / `achievement_unlocked {id, grade}` / `leaderboard_viewed {scope}` / `leaderboard_opt_in {on}` / `frame_equipped {frame}` / `profile_shared {surface}` (`leaderboard` = the profile page, `leaderboard_wrapped` = the year page: one event, two surfaces) / `handle_claimed`. The funnel that decides whether any of this was worth building is **`recap_shown` -> `recap_shared` -> `/r/` pageview -> `/download` -> `app_opened`**; nothing else in the feature matters if that one does not convert. `recap_shared` surfaces are `room_exit` (the offer on the way out) and `manage` (went back for the link) - **one event, because splitting it splits that funnel**. `recap_deleted` is its only counter-signal: a share taken back was not a share, and the view count rides along because taking back a link people were actually opening means something different again. `handle_claimed` is the only measure of the one thing Premium adds here; the handle itself is never sent.
- **Tier events** are `room_extended` / `room_resumed` / `room_deleted` / `limit_hit {which}` / `upgrade_cta_shown` / `upgrade_cta_clicked {surface}`. `limit_hit` keeps the property name `which` that the shipped events already use - the newer plan text says `kind`, but a single event with two property names splits its own funnel. Surfaces so far: `room_expiry`, `room_limit`, `leaderboard`, `handle`, `voice_lock`. **`upgrade_cta_shown` has to fire wherever `upgrade_cta_clicked` can** - clicks with no impressions leave the conversion rate uncomputable, which is the whole reason the two exist as a pair. Where the prompt is an inline card rather than a dialog there is no "shown" moment to hang it on, so it fires **once per visit from a lifecycle point, never from `build`** (which would report it every frame): see `_trackUpsellShown` on the leaderboard and `_trackHandleUpsellShown` on the profile.
- **Opting out is a hard stop, and it is read before `init`.** `AnalyticsConsent` (shared_preferences) is loaded in `_bootstrap` *before* `Analytics.init`, so someone who opted out never emits even `app_opened`. `setOptedOut(true)` drops the queue and cancels the timer rather than filtering at the send point, and opting back in resumes from silence rather than replaying what was withheld. The toggle lives in the profile screen for guests and account holders alike. Release builds report when `POSTHOG_API_KEY` is provided via `--dart-define`.
